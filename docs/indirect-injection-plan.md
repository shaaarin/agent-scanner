# План: тестирование агента на косвенные промпт-инъекции

## Что делаем

Добавляем тип скана «Косвенные инъекции». Платформа запускает агента,
отправляет ему обычную задачу по его назначению и, пока он работает,
подкладывает инъекцию в результаты его инструментов (tools). Потом
сравниваем поведение агента с прогоном без инъекции. Так каждый вызов
инструмента можно проверить разными payload'ами. В агенте ничего не меняем.

## Идея интеграции

Инструмент выполняется внутри агента, поэтому его ответ через прокси не
проходит. Но после вызова агент отправляет результат в LLM следующим
запросом `chat/completions`, в сообщении `role: tool`, и этот запрос
проходит через mitm-сайдкар. Прокси дописывает payload в это сообщение
до того, как запрос уйдёт к LLM:

```
assistant: tool_calls=[{id: "call_1", function: {name: "search_docs"}}]
tool:      tool_call_id="call_1", content="<реальный результат>" + PAYLOAD
```

Для LLM это выглядит так, будто payload вернул сам инструмент. Способ
работает для любых инструментов (локальных, БД, файлов, HTTP), и агента
не нужно настраивать.

## Как работает

1. **Базовый прогон.** Сканер отправляет агенту обычную задачу без
   инъекции. Из перехваченного трафика (`TrafficEvent`) видно, какие
   инструменты вызывались и в каком порядке: это точки для инъекций, а
   ответ агента становится эталоном.
2. **Фаззинг.** Для каждой комбинации «задача × точка (tool, номер вызова)
   × payload» сканер создаёт в control-api активный прогон (`InjectionTrial`)
   и снова отправляет агенту ту же задачу.
3. **Подмена в прокси.** На каждом `chat/completions` прокси берёт из
   control-api директиву активного прогона, находит нужное сообщение
   `role: tool` и дописывает в него payload. Событие помечается
   `trial_id` и `injected=true`. Агент каждый раз отправляет всю историю
   заново, поэтому подмена применяется в каждом запросе прогона.
4. **Оценка** — по трафику прогона:
   - перехват вызова инструмента: payload просит вызвать инструмент с
     контрольным значением (канарейкой), например `send_email(to=x7q@canary)`,
     и это видно в `tool_calls` ответа LLM;
   - канарейка в ответе: контрольный токен или ссылка в финальном ответе
     агента;
   - уход от задачи: модель-судья сравнивает ответ с эталоном.
5. **Результат** — доля успешных атак (ASR) по инструменту, семейству
   payload'ов и задаче, со ссылками на трафик каждого прогона.

Ответы LLM недетерминированы, поэтому каждая комбинация прогоняется
несколько раз (`repeats`).

## Решение

- Новый тип скана `indirect_injection` и отдельный сервис
  `scanner/indirect` (`scanner-indirect`) с обычным контрактом сканера;
  запуск и ожидание агента — как в `scanner-deepteam`.
- В control-api новая таблица `InjectionTrial` (задача, точка, payload,
  статус, вердикт) и эндпоинт `GET /scans/{id}/injection/active` для
  прокси.
- В `TrafficEvent` добавляем `trial_id`, `injected`, `injection_target`
  (аддон уже отправляет последние два поля, но в модели их нет). Нужна
  миграция Alembic.
- Прокси меняет тело запроса **только** в скане этого типа, в остальных
  остаётся только наблюдателем. Директиву берёт без кэша, иначе она
  попадёт в следующий прогон.
- Payload'ы — YAML-шаблоны в `scanner/indirect/app/payloads/` с
  плейсхолдерами `{{canary}}`, `{{tool_name}}`, `{{user_task}}`. Семейства:
  «игнорируй инструкции», поддельные системные теги, подделка структуры
  ответа, эксфильтрация через ссылку, перехват вызова инструмента.
- Задачи задаются в `Scan.config` или генерируются моделью-судьёй по
  `agent_purpose`.
- Прогоны в одном скане идут последовательно: прокси не может отличить
  параллельные диалоги одного Pod'а.

## Этапы

1. **control-api.** `InjectionTrial`, поля `TrafficEvent`, миграция,
   эндпоинты директивы и прогона, `indirect_injection` в `ScanType` и
   `SCANNERS`.
2. **proxy.** Режим `append` для `chat/completions`: любой инструмент или
   инструмент по имени, номер вызова. Пересобрать образ и запушить его в
   `kind-registry`.
3. **scanner/indirect.** Фазы: Инициализация → Запуск агента → Ожидание
   агента → Базовый прогон → Фаззинг → Оценка → Сохранение результатов.
   Задачи задаются вручную, 5–10 статичных payload'ов, оценка по
   канарейкам.
4. **web.** Тип «Косвенные инъекции» в форме (задачи, инструменты,
   семейства payload'ов, `repeats`, `max_trials`), матрица «инструмент ×
   payload» и переход к трафику прогона.
5. **Проверка и документация.** Живой прогон на kind на тестовом агенте
   с инструментами; обновить `AGENTS.md` и `docs/architecture.md` (§6:
   прокси теперь может менять тело запроса).
6. **Дальше.** Модель-судья и генерация задач; адаптивные payload'ы
   (судья переписывает payload под реальный результат инструмента);
   режимы `prepend`/`replace`/`wrap`; форматы `/responses` и Anthropic
   `/messages`; инъекция прямо в HTTP-ответы внешних API, которые
   вызывает инструмент.

## Что согласовать
- **Меняется принцип прокси.** Сейчас в документации сказано, что тело
  запроса не переписывается. Для этого типа скана оно переписывается.
- **Форматы API.** Сначала поддерживаем только `chat/completions`.
  Агенты на Responses API или Anthropic API в первой версии не
  тестируются.
