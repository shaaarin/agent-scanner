# MCP: реализация и проверка

Пользовательская документация находится на сайте `/help` (выбор движка,
форматы источников, примеры, результаты, команды и устранение ошибок).

## Редактирование активов в интерфейсе

Во всех трёх вкладках «Активы» используется общий блок действий:
нейтральная кнопка «Изменить» и красная «Удалить» одинакового размера.
Редактор MCP сохраняет имя/описание, настройки текущего источника
(адрес, заголовки, Git/ref/окружение или MCPB/user_config) и деплой через
существующий `PUT /mcp-assets/{id}`. MCPB можно заменить новым локальным
файлом или архивом по HTTPS URI; сначала загружается и проверяется новый
неизменяемый артефакт. Прежний артефакт и снимки целей в старых сканах
не переписываются. Тип источника в этом редакторе не меняется.

Для skills доступно редактирование имени/описания и параметров репозитория
через `PUT /skill-assets/{id}`. Пустое поле Git-токена сохраняет прежнее
значение, отдельный флаг явно удаляет токен. У ZIP-skill меняются метаданные,
а содержимое архива сохраняется: API замены ZIP пока нет. Кнопка «Отмена»
не отправляет изменения актива.

Проверка выполняется на собственных тестовых активах через UI с последующим
чтением API: remote-MCP, репозиторий с нестандартным config_path/окружением,
MCPB с заменой архива, Git- и ZIP-skills. Проверяются сохранность прежнего
скана, токена при пустом поле и ZIP при изменении метаданных, ошибки JSON,
отмена и одинаковые размеры/цвета действий на всех трёх вкладках.

## Контейнеры и API

`control-api` направляет MCP-сканы в координатор `scanner-mcp`.
Координатор планирует scanner_ids, отправляет каждую задачу в отдельный
scanner-mcp-{engine}, собирает результаты и пишет жизненный цикл скана.
Worker принимает только собственный engine. Доступность контейнеров и
наличие ключа Snyk видны при создании сканирования в MCP-активе — список
движков приходит из `GET /scanners` (схема scanner-mcp), отдельной
страницы «MCP-сканеры» больше нет.
`/schema` использует живой `/engines`: координатор параллельно опрашивает
каждый worker (не более 0,75 с на запрос), проверяет идентификатор движка
и его `available/reason`. Недоступный или некорректно отвечающий worker
отключается в форме с причиной; весь MCP-сканер из-за этого не скрывается.
Отсутствие ключа Snyk определяется его собственным контейнером, а не
окружением координатора. Дополнительно API фильтрует применимость к цели.
Схема кэшируется control-api до 30 секунд и загружается при открытии формы:
после изменения состояния worker дождитесь истечения кэша и откройте форму
заново. Это снимок доступности, не гарантия успешного последующего запуска.
Планировщик не исключает недоступные движки из явного списка или фиксированного
набора по умолчанию: их ошибки по-прежнему попадают в независимые отчёты.
Для MCPB в каждую задачу передаются `artifact_id` и `target.user_config`
из сохранённой конфигурации скана (также поддерживается прежний плоский
конфиг с `mode: bundle`). Отсутствующий `user_config` означает `{}`.
Существующий запускатель бандла передаёт скалярные значения `user_config`
как переменные окружения процесса MCP, поверх окружения из манифеста:
строки, числа и bool преобразуются через `str`, объекты/массивы/null
не передаются напрямую в окружение. Шаблоны `${user_config.*}` разрешаются
отдельно в команде, аргументах и окружении манифеста (см. ниже).
Semgrep получает параметры в задаче,
но не запускает сервер и не использует его окружение.
Рабочие контейнеры не публикуют порты хоста, имеют лимиты CPU/памяти/PID,
cap_drop ALL, no-new-privileges. Каждое задание движка выполняется в отдельном
интерпретаторе под контролем worker: общий таймаут включает импорт/инициализацию,
скачивание MCPB, установку зависимостей, MCP-сеанс и CLI-анализ. Лимит вывода
и JSON-отчёта — 8 МБ. Worker остаётся отдельным обслуживающим процессом.

По общему таймауту worker посылает SIGTERM группам процессов этого задания,
ждёт до 3 секунд, затем завершает оставшиеся процессы через SIGKILL и проверяет
их остановку (до 2 секунд). Учитываются отдельные сессии MCP SDK и CLI:
потомки отслеживаются через Linux `/proc`, время рождения PID и наследуемый
маркер задания. Маркер не берётся из пользовательской конфигурации. Если
остановку подтвердить не удалось, возвращается отдельная ошибка, а не сообщение
об успешной остановке. Это управление жизненным циклом доверенного тестового
стенда, не изоляция от кода, намеренно скрывающего потомков и очищающего маркер.

Ожидание HTTP-ответа координатором длиннее лимита worker с запасом на очистку.
Результат таймаута возвращается после остановки процессов; слот worker
освобождается, ошибка сохраняется в отчёте движка и журнале, координатор
продолжает следующий движок. Успешно сохранённые результаты не теряются.
При нормальном завершении также очищаются оставшиеся потомки задания.
Отдельная HTTP-команда пользовательской отмены здесь не добавляется.

Исходники анализируются без исполнения. Архивы ограничены размером,
количеством файлов, путями и запретом symlink. Публичный Git клонируется
по HTTPS без редиректов и запуска install scripts. Приватный Git клонируется
с токеном из актива (oauth2:<token>@host, как в launcher). URL к внутренним компонентам платформы,
link-local и metadata запрещены; частные тестовые MCP-сети допускаются.
Это локальный стенд, не многопользовательская система для недоверенных
пользователей: сетевой egress и DNS rebinding требуют отдельного усиления.

## Воспроизводимые проверки

```sh
docker compose -f compose.local.yml --profile test up -d --build
python3 scripts/smoke_mcp.py
```

Скрипт использует настоящие API, CLI/SDK upstream и живой FastMCP-сервер.
Проверяются четыре опасные операции Python, безопасный контроль, SSRF,
TypeScript eval, точность вне MCP-декоратора, MCPB upload/storage/scan,
Cisco YARA по каталогу и живому MCP, Readiness, Prompt Defense,
MCPRadar по каталогу и живому MCP, успешные реальные echo/add и намеренно
нарушенное ожидание ответа. Отчёт с ID сканов: mcp-smoke-results.json.
Snyk не тестируется без ключа; в результатах это нельзя считать успехом.

Передача настроек MCPB проверяется отдельно:
`python3 scripts/smoke_mcp_user_config.py --output /tmp/mcp-user-config.json`.
Скрипт загружает собственный безопасный Python-бандл без установки зависимостей
и запускает пять локальных движков, которым нужен работающий MCP.
Сервер проверяет настройки при старте (включая `0`, `false`, число и
переопределение окружения манифеста); динамический движок вызывает его инструмент.
Проверяются также ожидаемый отказ без обязательных настроек и совместимость
с пустым/отсутствующим `user_config` для бандла без обязательных настроек.
Фикстуры сохраняются для просмотра. Ключей и облачных вызовов нет.

### MCPB: подстановки в команде запуска

Описание переменных и разворачивания списков:
[MCPB Manifest — MCP Configuration / User Configuration](https://github.com/modelcontextprotocol/mcpb/blob/main/MANIFEST.md#mcp-configuration).

Запускатель раскрывает `${__dirname}`, `${HOME}`, `${DESKTOP}`,
`${DOCUMENTS}`, `${DOWNLOADS}`, `${pathSeparator}` / `${/}` и
`${user_config.KEY}` в `server.mcp_config.command`, `args`, `env`.
Пути относятся к временному каталогу бандла внутри Linux-worker, не к
домашнему каталогу пользователя или секретному окружению сервиса.
Каталоги Desktop/Documents/Downloads автоматически не создаются и не
предоставляют доступ к файлам пользователя.

Если значение настройки не задано, используется `user_config.KEY.default`
из манифеста; в строковых defaults поддерживаются встроенные переменные.
Отсутствующая обязательная настройка или переменная, неизвестная переменная,
объект вместо скаляра, некорректные `args/env` дают ошибку до установки
зависимостей и запуска. Значения настроек в эти сообщения не включаются.
Числа и boolean в шаблонах превращаются в строки (`0`, `false`, `true`).
Список в отдельном аргументе `${user_config.KEY}` разворачивается в несколько
аргументов; списки в составной строке или `env` отклоняются как неоднозначные.

Подстановка однопроходная, без shell: пробелы и метасимволы в значении
не разбивают аргумент, а `${...}` внутри пользовательского значения остаётся
буквальным текстом. Прежняя прямая передача скаляров `user_config` в окружение
с `str(bool)` сохранена для совместимости; она по-прежнему приоритетнее `env`
манифеста при совпадении имён. Это не полная реализация MCPB: platform_overrides,
проверка всей схемы типов/диапазонов настроек и дополнительные рантаймы здесь
не добавляются.

```sh
docker compose -f compose.local.yml exec -T scanner-mcp python < scripts/check_mcpb_variables.py
python3 scripts/smoke_mcpb_variables.py --output /tmp/mcpb-variables.json
python3 scripts/smoke_mcp_user_config.py
python3 scripts/smoke_mcpb_manifest.py
```

Первая проверка вызывает настоящий сборщик команды на временных фикстурах.
Живая проверка загружает безопасный автономный MCPB, запускает Semgrep и пять
локальных runtime-движков, проверяет `command/args/env`, defaults, списки,
пробелы/метасимволы, `0/false`, буквальный `${HOME}` в пользовательском значении
и реальный вызов `ready`. Отдельные сканы подтверждают отказ при отсутствующей
настройке и неизвестной переменной. Старые проверки контролируют совместимость
окружения без шаблонов и SAST/распаковки манифеста.

### MCPB: Python-зависимости в окружении запуска

При наличии `requirements.txt` pip устанавливает зависимости в
`.bundle-deps` текущего бандла. После успешной установки этот путь добавляется
в начало `PYTHONPATH` **дочернего MCP-процесса**; следом сохраняется значение
из манифеста или пользовательской конфигурации. Глобальный `os.environ`
worker-процесса не изменяется: параллельные бандлы не наследуют пути друг друга.
Без `requirements.txt` окружение запуска не дополняется; ошибка pip по-прежнему
останавливает запуск этого движка, не выдавая его за успешную проверку.

```sh
docker compose -f compose.local.yml exec -T scanner-mcp python < scripts/check_mcpb_dependencies.py
python3 scripts/smoke_mcpb_dependencies.py --output /tmp/mcpb-dependencies.json
```

Проверки устанавливают собственные безопасные wheel-фикстуры через pip
с `--no-index`, без внешних зависимостей и обращения в интернет. Два бандла
используют одноимённую библиотеку с разным содержимым и дополнительный модуль
из `PYTHONPATH` манифеста. Настоящие MCP-сеансы проверяют импорты, ответы своих
версий библиотеки и сохранность путей. Проверка внутри worker также сравнивает
глобальное окружение до/после, покрывает отсутствие requirements и ошибку pip.
Живой API-сценарий запускает два скана с пятью локальными runtime-движками.

### Общий таймаут и остановка задания движка

```sh
docker compose -f compose.local.yml exec -T scanner-mcp python < scripts/check_mcp_task_stop.py
python3 scripts/smoke_mcp_timeouts.py --worker-container <имя-контейнера-mcp-dynamic> --output /tmp/mcp-timeouts.json
```

Первая проверка создаёт собственные спящие процессы: штатный обработчик TERM,
потомка в отдельной сессии, игнорирующего TERM, и независимый соседний процесс.
Проверяются льготный период перед KILL и отсутствие живых остатков.
Живой сценарий использует безопасный MCPB: MCPRadar успешно снимает каталог,
динамическая проба зависает, её потомок игнорирует TERM, после таймаута Cisco
YARA успешно продолжает скан. Одновременно другой динамический скан завершается
успешно; проверяется отсутствие оставшегося fixture-процесса в worker и запуск
следующего задания после освобождения слота. Отдельный скан с медленным стартом
MCP проверяет общий таймаут до начала CLI-анализа и итоговый статус failed.
Регрессия: `smoke_mcp_isolation.py`, `smoke_mcpb_dependencies.py`,
`smoke_mcpb_variables.py`, `smoke_mcp_user_config.py`, `smoke_mcpb_manifest.py`.

### MCPB: чтение манифеста при статическом анализе

Ошибка «В корне MCPB отсутствует manifest.json» воспроизводилась даже после
успешной загрузки корректного архива: API читал метаданные отдельно, а worker
в режиме `code_only=True` сначала отбрасывал все файлы, кроме исходников.
JSON-манифест пропускался, поэтому его последующее чтение не выполнялось.

Обработка разделена на получение архива и распаковку: сначала проверяются
общие ограничения и пути **всех** записей, затем отдельно читается корневой
`manifest.json`, и только после этого выбираются файлы для распаковки.
В SAST извлекаются только поддерживаемые исходники; в динамическом режиме —
весь архив, включая манифест и ресурсы. Порядок записей ZIP не влияет на чтение
манифеста. Отсутствующий манифест, некорректный JSON и JSON не объектом имеют
раздельные сообщения об ошибке. Worker также проверяет лимит манифеста 1 МиБ,
уже действующий в upload API. Ограничения 50 МиБ/5000 записей/250 МиБ,
проверки путей и запрет symlink сохранены.

Проверки без новых тест-фреймворков:

```sh
docker compose -f compose.local.yml exec -T scanner-mcp python < scripts/check_mcpb_archive.py
python3 scripts/smoke_mcpb_manifest.py --output /tmp/mcpb-manifest.json
python3 scripts/smoke_mcp.py
python3 scripts/smoke_mcp_user_config.py
```

Первая проверка вызывает настоящий распаковщик на ZIP-фикстурах в обоих режимах,
проверяет выбранные файлы и отклонение некорректных/небезопасных архивов до записи.
Вторая проходит upload/storage/сканирование: манифест первым и последним,
Semgrep и динамический вызов инструмента из одного бандла, ошибки upload API.
Общий smoke-скрипт содержит корректную обязательную `server.mcp_config.command`.
Тестовые бандлы не требуют установки зависимостей и не вызывают опасные инструменты.
Исправление не расширяет поддержку CJS/MJS или лимит размера файлов Semgrep;
это отдельные ограничения анализатора, а не ошибка чтения манифеста.

## Перезапуск сканов и отдельных движков

### Источник цели и неизменяемый снимок

При `POST /scans` для MCP цель берётся только из `McpAsset.config` и
сохраняется в `Scan.config.target`. Входной `config` содержит параметры
проверок, но не цель: наличие ключа `config.target` отклоняется с HTTP 422,
даже если передана та же цель или null. Отклонённый запрос не создаёт скан.
Дополнительно при сборке конфигурации цель актива записывается последней,
поэтому параметры проверок не могут её перекрыть.

Редактирование актива применяется к новым сканам. Запуск ранее созданного
скана и повторные попытки `all`/`failed`/`engine` используют сохранённый снимок,
не перечитывают актуальный target актива и не переписывают исходные отчёты.

```sh
python3 scripts/smoke_mcp_target_snapshot.py --output /tmp/mcp-target-snapshot.json
```

Проверка через настоящий API отклоняет подмену/дублирование/null цели, проверяет
отсутствие созданных строк после отказа и сохранение параметров проверок.
Затем меняет только собственный тестовый актив на недоступный адрес с другим
транспортом/заголовками: новый скан получает новую цель, старый успешно
подключается по исходной. Проверяются все три режима повторов и сохранность
конфигурации, результатов и статуса исходных запусков. Ожидаемые ошибки проб
используются только для проверки повторов failed/all, без вызова инструментов.

В карточке скана и списке сканирований проваленный (`failed`) или частично
выполненный (`partially_failed`) скан можно повторить целиком. В карточке MCP
дополнительно доступны «Повторить незавершённые движки» и повтор одного движка
исходного плана, включая успешно отработавший. Незавершённые — это движки с
ошибкой или без сохранённого успешного результата после прерывания координатора.
Находки и failed checks при успешной работе движка не делают его незавершённым.

Каждый повтор создаёт **отдельный Scan**, сохраняет ссылки на предыдущую
попытку и корневой скан. Новая попытка имеет собственные session_id, статус,
журнал и отчёт; метаданные запуска агента не копируются. Исходные записи
сохраняются, в карточке видна история со ссылками. Отчёты разных попыток
не объединяются: успешный повтор одного движка не означает успешного выполнения
всего первоначального набора. Повтор динамического движка заново выполняет
сохранённые probes с теми же разрешениями; это может повторить побочные эффекты.

MCP-цель (URL/заголовки, Git/ref/токен, artifact_id/user_config), таймауты и
разрешения берутся из сохранённого конфига скана. Изменение актива на повтор
не влияет. Полный повтор оставляет `scanner_ids: []` пустым — применяется
фиксированный набор по типу цели из текущего кода, как при обычном запуске.
Для повтора части набора в конфиг новой попытки записываются конкретные ID.
Git-ветка или удалённый сервер к моменту повтора могут измениться; побайтовое
воспроизведение их прежнего состояния не гарантируется. MCPB повторно берётся
из того же неизменяемого артефакта, без новой загрузки.

API:

```sh
curl localhost:8000/scans/ID/retries
curl -X POST localhost:8000/scans/ID/retry -H 'Content-Type: application/json' -d '{"mode":"all"}'
curl -X POST localhost:8000/scans/ID/retry -H 'Content-Type: application/json' -d '{"mode":"failed"}'
curl -X POST localhost:8000/scans/ID/retry -H 'Content-Type: application/json' -d '{"mode":"engine","engine_id":"cisco_readiness"}'
```

`POST /retry` возвращает новую попытку, которую запускает через обычный
`/start`. Если координатор недоступен, новая попытка получает `failed` и может
быть повторена снова. В одной истории допускается только одна pending/running
попытка: параллельный запрос получает 409, UI показывает ссылку на активную.
Неподходящий движок или некорректное тело запроса отклоняются до создания
попытки. Pending/running нельзя повторять. Исторические MCP-сканы с
`completed` и `summary` получают те же действия, что соответствующий итоговый
статус в UI. Удаление скана с дочерними попытками и выполняющегося скана
возвращает 409; конечную завершённую попытку можно удалить отдельно.

Проверка использует настоящие PostgreSQL, API, координатор и workers; временно
останавливает Readiness и координатор. Запускать только на изолированном стенде
без чужих активных сканов. В `finally` оба сервиса восстанавливаются:

```sh
python3 scripts/smoke_mcp_retries.py --compose-file compose.local.yml --output /tmp/mcp-retries.json
```

Проверяются полный и частичный повтор при недоступном движке и после его
восстановления, пустой выбор, сохранность конфига после правки актива,
неизменность прежних отчётов и журналов, история, защита от двойного запуска,
повтор динамического MCPB, оставшийся план после перезапуска координатора
и отказ отправки задачи в недоступный координатор. Тестовые записи сохраняются.
Отдельная проверка полного повтора скана агента рассчитана на этот локальный
Compose-стенд без DeepTeam: проверяется отказ передачи задачи, LLM не вызывается.

  и не оценка устойчивости LLM-агента к prompt injection.

Эвристики описаний и AST покрывают разные поверхности. Применять их
совместно и подтверждать наиболее важные находки динамическими сценариями.
Нулевой отчёт не доказывает безопасность; ошибка анализа не является чистым
результатом. В интерфейсе выводится область покрытия каждого движка.

## Независимое выполнение движков

Координатор выполняет план последовательно. HTTP-ошибка, таймаут, недоступный
worker или некорректный JSON-отчёт становятся ошибкой только этого движка:
следующий движок запускается независимо. Правила выбора `scanner_ids`,
включая фиксированные наборы для пустого списка, не изменены.

После каждого движка весь накопленный отчёт сохраняется в `Scan.results`.
У каждого результата есть `status: success|failed`, `error`, метаданные
движка и длительность. Неуспешный движок не даёт подтверждённого покрытия;
его пустой `findings` нельзя интерпретировать как отсутствие уязвимостей.
Находка или failed check сами по себе не являются ошибкой выполнения.

Сохранена совместимость: один движок возвращает плоский отчёт, несколько —
`engine: mcp-suite`, массив `runs` и объединённые `findings`. Добавлен
`summary: {total, completed, failed, pending}`. `pending` — число движков
без окончательного результата, включая выполняемый. Промежуточный отчёт
набора имеет `status: running`, итоговый — `success`, `partially_failed`
или `failed`. Старые отчёты без этих полей по-прежнему читаются UI.

Итоговый `Scan.status` для MCP:

- `success` («Успешно выполнено») — все движки отработали;
- `partially_failed` («Частично выполнено») — есть успешные результаты,
  но также ошибки движков или прерывание оставшейся работы;
- `failed` («Ошибка») — нет ни одного успешно завершённого движка.

`pending`/`running` остаются промежуточными статусами. Найденная уязвимость
или failed check не делает успешное выполнение движка ошибкой.
При частичном результате UI предупреждает о неполном покрытии. Клиенты
должны проверять `summary`, а не считать `success` или ноль находок
доказательством безопасности. Временные сбои control-api обрабатываются
ограниченными повторами (см. ниже). После исчерпания повторов checkpoint
оставшиеся движки не запускаются: координатор пытается сохранить частичный
отчёт, включая самый свежий результат, который ещё не удалось записать.
При наличии успешных результатов статус будет `partially_failed`, иначе
`failed`, если финальная запись в API удалась. Перезапуск прерывает скан;
автоматическое продолжение и exactly-once исполнение не реализованы.

### Временная недоступность control-api

MCP-клиент повторяет чтение скана, запись checkpoint/фазы/финального статуса
и отправку журнала при сетевых ошибках, таймаутах, `429` и `5xx`:
не более пяти попыток с паузами 1/2/4/8 секунд. Таймаут подключения —
2 секунды, остальных сетевых операций — 5 секунд. Остальные HTTP-ошибки,
включая `404` и `422`, не повторяются. Это политика MCP-клиента, не всех
сканеров платформы. Загрузка байтов MCPB в worker остаётся отдельным запросом.

Повторы checkpoint отправляют тот же накопленный отчёт; **вызовы `/execute`
движков и MCP-инструментов не повторяются**. Пока checkpoint не записан,
координатор не переходит к следующему движку. При восстановлении API в пределах
попыток скан продолжается с тем же планом и обычным итоговым статусом.
Сообщения о повторных попытках идут в контейнерный лог без тел запросов.

Ошибки отправки журнала проверяются по HTTP-статусу и не роняют скан.
После исчерпания попыток строка теряется с диагностикой в контейнерном логе.
При потере ответа после успешной записи POST повтор может создать дубликат
строки: дедупликация журнала пока не реализована.

**Граница гарантии:** постоянной очереди нет. Если control-api недоступен
и при финальной попытке сохранить ошибку, координатор пишет CRITICAL с ID
скана и счётчиками (без содержимого отчёта), освобождает слот, но не заявляет,
что финальный статус сохранён. В БД может остаться `running` и последний
успешный checkpoint. Более новые результаты остаются только в памяти до
выхода из обработки и затем теряются; восстановление API само по себе не
возобновляет их доставку. Перезапуск координатора помечает такой скан
прерванным на основе сохранённого checkpoint. Для гарантии при длительном
сбое/перезапуске нужна отдельная постоянная очередь доставки.

Живая проверка краткого отказа и исчерпания повторов (только изолированный
стенд без чужих сканов; скрипт временно останавливает API и восстанавливает
сервисы в `finally`):

```sh
python3 scripts/smoke_mcp_persistence.py --compose-file compose.local.yml --mode recovered
python3 scripts/smoke_mcp_persistence.py --compose-file compose.local.yml --mode exhausted
# Retry-политика на локальном HTTP fault-сервере, без LLM/сканерных моков:
docker compose -f compose.local.yml exec -T scanner-mcp python < scripts/check_mcp_control_retries.py
```

Первый сценарий проверяет сохранение отчётов всех трёх движков после отказа;
второй — остановку оставшегося плана и сохранение двух результатов, включая
последний неотправленный. Тестовые записи сохраняются для просмотра.

Миграция `0010_mcp_scan_statuses` обеспечивает место для новых значений в
строковой колонке. Исторические строки не пересчитываются. Статус
`completed` остаётся для старых сканов и остальных типов сканирования;
UI старых MCP-отчётов с `summary` вычисляет подпись по тем же правилам.

Живая проверка без моков и новых тест-фреймворков:

```sh
python3 scripts/smoke_mcp_isolation.py
# Только на отдельном тестовом стенде без чужих активных сканов:
docker compose -f compose.local.yml stop scanner-mcp-cisco-readiness
python3 scripts/smoke_mcp_isolation.py --expect-readiness-down
docker compose -f compose.local.yml start scanner-mcp-cisco-readiness
```

Worker необходимо восстановить и при неуспешном тесте. Скрипт создаёт
собственные актив/сканы и оставляет их для просмотра. Проверяет ошибку
в начале/середине/конце плана, пустой список, одиночный движок и сохранение
уже видимых промежуточных результатов. HTTP API и URL тестового MCP можно
переопределить через `MCP_TEST_API` и `MCP_TEST_TARGET`.

Для проверки доступности без ключа Snyk используйте
`python3 scripts/smoke_mcp_availability.py --state healthy`. После остановки
Readiness-worker — `--state readiness-down`, после остановки всех семи
workers (не координатора) — `--state all-down`. Скрипт ожидает истечения
кэша и проверяет причины, фильтрацию по типу цели и неизменность схемы
для остальных активов. После теста восстановите workers и повторите
`--state healthy`. Фикстуры остаются доступны в интерфейсе.
