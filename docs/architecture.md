# Архитектура

## 1. Обзор

Agent Scanner проверяет LLM-агентов с вызовом инструментов. Тестируемый
агент подключается **без единой правки**: платформа прозрачно
перехватывает его исходящий HTTPS на сетевом уровне. Поверх этого
перехвата работают два сценария:

- **динамическое тестирование** — платформа запускает агента и прогоняет
  его атаками (DeepTeam), оценивая, следует ли агент инъекции;
- **наблюдение** — весь трафик агента к LLM журналируется, и по каждому
  обмену можно посмотреть тела запроса и ответа.

Отдельно от перехвата работает **анализ кода**: платформа клонирует
репозиторий агента и проверяет исходники через promptfoo code-scans, не
запуская агента (см. §7.2 и [`code-scan-architecture.md`](code-scan-architecture.md)).

## 2. Компоненты

```
                 └───────────┘        └──────┬───────┘

                      ┌──────────────────────┴────────────────────────┐
                      │ deep_team                                     │ code_scan
                      ▼                                               ▼
             ┌──────────────────┐ build/launch ┌──────────┐ ┌───────────────────┐
             │ scanner-deepteam │─────────────▶│ launcher │ │ scanner-promptfoo │
             └────────┬─────────┘              └────┬─────┘ └─────────┬─────────┘
                      │ DeepTeam (LLM)              │ k8s             │ git clone +
                      ▼                             ▼                 │ promptfoo code-scans
                ┌───────────┐               ┌───────────────┐         ▼
                │ провайдер │               │ Pod агента +  │ ┌───────────────────┐
                │   LLM     │               │ mitm-proxy    │ │  Promptfoo Cloud  │
                └───────────┘               └───────┬───────┘ └───────────────────┘
                                                    │ перехват
                                                    ▼
                                              ┌───────────┐
                                              │  proxy    │
                                              └─────┬─────┘
                                                    │ TrafficEvent
                                                    ▼
                                               control-api
```

| Сервис | Назначение |
|---|---|
| `control-api` | FastAPI + SQLModel/SQLite. Хранит модели, конфиги агентов, сканы, журналы и события. Применяет миграции Alembic на старте. |
| `proxy` | mitmproxy-аддон (`proxy/addon.py`). Точка перехвата трафика агента; журналирует запросы/ответы и помечает клиента. |
| `scanner-deepteam` | `scanner/deepteam`. Скан `deep_team`: поднимает агента через `launcher`, прогоняет DeepTeam, пишет фазы/журнал/результаты. |
| `scanner-promptfoo` | `scanner/promptfoo`. Скан `code_scan`: клонирует репозиторий агента, прогоняет `promptfoo code-scans`, пишет фазы/журнал/находки. Без kind и launcher. |
| `launcher` | Собирает образ агента в кластере (git-clone + Kaniko) и запускает Pod с MITM-сайдкаром. Работает с внешним кластером по kubeconfig, без Docker-сокета. |
| `web` | Дашборд (React/Vite). Текст интерфейса — на русском. |
| `control-api-mitm-bridge`, `launcher-mitm-bridge` | `alpine/socat`-форвардеры, владеющие опубликованным на хост портом вместо dual-homed сервисов (особенность WSL2/Docker Desktop, см. `CLAUDE.md`). |

## 3. Как агент подключается (MITM pivot)

Агент запускается как Pod, в котором три вещи обеспечивают перехват, не
затрагивая приложение:

1. **`ca-trust-setup`** (initContainer) пишет в общий `emptyDir` связку
   «системные CA + корневой CA платформы» и монтирует её поверх системного
   файла доверенных сертификатов агента.
2. **`net-setup`** (initContainer, `NET_ADMIN`) добавляет правило iptables
   NAT REDIRECT, отправляющее исходящий TCP/443 на сайдкар (кроме трафика
   самого сайдкара по uid).
3. **`mitm-proxy`** (сайдкар) — образ `proxy` в прозрачном режиме,
   терминирует TLS и переподписывает соединение своим CA.

`launcher/app/pod_manager.py` собирает этот Pod. Сайдкару передаётся
`SESSION_ID` (= `Scan.session_id`), по которому `control-api` связывает
перехваченный трафик со сканом.

Известные ограничения:

- приложения, использующие собственный встроенный стор CA (`certifi` и
  подобные), не видят корневой CA платформы — их нужно настраивать отдельно;
- правило iptables применяется до старта сайдкара, поэтому соединение в
  узком окне запуска Pod может упасть (реальные клиенты обычно
  повторяют запрос).

## 4. Жизненный цикл сканирования

1. `POST /scans` создаёт `Scan` со статусом `pending`.
2. `POST /scans/{id}/start` (control-api):
   - очищает журнал скана, ставит `running` и фазу `Запуск`;
   - синхронно дёргает сканер своего типа (`POST <url сканера>/run/{id}`,
     связка «тип → сервис» — `SCANNERS` в `control-api/app/api/scans.py`).
     Сканер отвечает сразу и выполняет работу в фоне. Для типа без сканера
     запуск отклоняется с 400 ещё до перевода в `running`; если сканер
     недоступен или ответил ошибкой — скан сразу `failed`.
3. `scanner-deepteam` проходит фазы, записывая `ScanLog` и текущую фазу в `Scan`
   (фазы `scanner-promptfoo` — в §7.2):
   - **Инициализация** — читает скан, конфиг агента и модель-судью;
   - **Запуск агента** — `POST launcher/launch {scan_id}` (сборка может
     занять минуты);
   - **Ожидание агента** — опрашивает `launcher/status/{scan_id}` до
     `Running`, затем ждёт ответа HTTP-поверхности агента (LangGraph — `/ok`,
     REST API — `api_config.health_path`, по умолчанию путь эндпоинта без `/chat` + `/ok`).
     Адрес агента берётся из ответа `/launch` (`agent_config_patch`), а не
     из `AgentConfig`: конфигурация общая, и параллельный скан того же
     агента перезаписывает в ней адрес своим подом;
   - **Тестирование** — запускает DeepTeam, стримя его вывод в журнал
     этого скана (вывод маршрутизируется по потоку, поэтому параллельные
     сканы не смешивают журналы);
   - **Сохранение результатов** — пишет результаты, останавливает агента
     (`launcher/stop`, namespace удаляется) и переводит скан в `completed`.
     Последняя строка журнала пишется до смены статуса: UI перестаёт
     опрашивать журнал, как только видит `completed`.
4. Любая ошибка журналируется (уровень `error`) и переводит скан в
   `failed` с текстом в `Scan.error`. Для DeepTeam ошибкой считается и
   прогон, в котором ни один кейс не удалось оценить (например, провайдер
   LLM отвечает `RateLimitError`): таблица упавших кейсов остаётся в
   `Scan.results`. Если ошибкой завершилась только часть кейсов, скан
   `completed`, а в журнале — предупреждение. Если агент уже ответил по
   HTTP, его namespace удаляется и при ошибке; если не поднялся —
   остаётся для `kubectl logs`, подсказка есть в тексте ошибки.
   Скан, прерванный перезапуском сервиса-сканера, при старте сервиса
   переводится в `failed` («сервис был перезапущен»).
5. UI страницы скана опрашивает `GET /scans/{id}/logs?after_id=...` и
   `GET /scans/{id}` каждые 2 секунды, пока скан не завершён. Журнал
   отдаётся страницами по 500 строк, UI дочитывает его до конца.

Статусы: `pending`, `running`, `completed`, `failed`.
Типы: `deep_team` и `code_scan` (реализованы), `mcp` и `agent_skills`
(заглушки в UI, запуск отклоняется).

## 5. Модель данных

| Таблица | Назначение |
|---|---|
| `LLMModel` | Провайдер + модель + `base_url` + `api_key`. Хранится в открытом виде (принятый техдолг). Используется как модель-судья DeepTeam. |
| `AgentConfig` | Репозиторий (`git_repo_url`/`git_ref`/`git_access_token`), `dockerfile_path`, `env_example_path`, `env_vars`, `api_port`, `agent_purpose` (назначение агента для DeepTeam), `interaction_mode` (`none`/`api`/`langgraph`), `api_config`, `langgraph_config`. Агента со сканированиями удалить нельзя (409): SQLite не проверяет внешние ключи. |
| `Scan` | Параметры и состояние скана: `type`, необязательный `agent_config_id` (у MCP-цели его нет), `status`, `session_id`, JSON `config`, JSON `results`, `phase`, `error`, а также метаданные запуска (`agent_namespace`, `agent_pod_name`, `build_job_name`, `built_image`), `started_at`/`finished_at`. |
| `MCPArtifact` | Неизменяемый MCPB-архив: исходное имя и URI, SHA-256, размер, разобранный `manifest.json` и исходные байты в SQLite BLOB. Содержимое не отдаётся списковым API. |
| `ScanLog` | Строка журнала скана: `level` (`info`/`success`/`error`), `phase`, `message`, `created_at`. |
| `TrafficEvent` | Перехваченный обмен: `session_id`, `scan_id`, `flow_id`, `direction` (`request`/`response`), `provider`, `host`, `path`, полное тело `raw_excerpt`, `upstream_base_url`. |

`Scan.config` по типам:

- `deep_team`: `{"eval_llm_model_id": <id>, "vulnerabilities": [...], "attacks": [...]}`;
- `code_scan`: `{"min_severity": "low|medium|high|critical", "guidance": <текст|null>}`.
- `mcp`: `{"target": {...}, "scanner_ids": [...], "timeout_seconds": 30}`. `target.kind` принимает `remote` (`server_url`, `transport`, `headers`, `verify_tls`), `repository` (`git_repo_url`, `git_ref`, `git_access_token`, `config_path`, `env`) или `bundle` (`artifact_id`, `user_config`). Пустой `scanner_ids` означает все доступные проверки. Токены, заголовки и переменные окружения хранятся в открытом виде в рамках принятого техдолга MVP.

MCPB загружается через `POST /mcp-artifacts/upload` либо немедленно
материализуется из публичного HTTPS URI через `POST /mcp-artifacts/from-url`.
API ограничивает размер, число файлов и распакованный объём, запрещает
небезопасные пути и symlink, проверяет корневой `manifest.json`; URI не может
разрешаться во внутренний/loopback адрес. Архив не распаковывается и не
исполняется на этом этапе. Для будущего сканера доступны метаданные и
`GET /mcp-artifacts/{id}/content`.

`Scan.results` по типам: `deep_team` — `vulnerability_results` и
`overall_score` (§7.1), `code_scan` — `summary` и `findings` (§7.2).
`scan.type` в базе — строка, поэтому новый тип скана миграции не требует.

## 6. Прокси

`proxy/addon.py` работает как mitmproxy-аддон:

- перехватывает только `*/chat/completions`;
- журналирует запрос и ответ как `TrafficEvent` (`raw_excerpt` — полное
  тело, без обрезки);
- для потоковых (SSE) ответов накапливает чанки, чтобы залогировать
  собранное тело, при этом сам поток не меняет;
- перед отправкой помечает исходящий запрос:
  - `User-Agent: my-coding-agent/1.0` (настраивается
    `LLM_CLIENT_USER_AGENT`) — всегда;
  - `x-opencode-session: <SESSION_ID>` — только для хостов `opencode.ai`.

Сканер делает то же самое для собственных вызовов к провайдеру
(`scanner/deepteam/app/deepteam_runner.py::provider_headers`), используя
`Scan.session_id` как стабильный идентификатор диалога.

## 7. Сканеры

Каждый тип скана выполняет свой сервис из `scanner/<имя>` со своим образом
и зависимостями. Контракт у всех один:

- `GET /health`;
- `POST /run/{scan_id}` — ответ сразу, работа в фоновом потоке, повторный
  запуск того же скана игнорируется;
- фаза, журнал и результат пишутся в control-api через `PATCH /scans/{id}`
  и `POST /scans/{id}/logs`; ошибка — `failed` с текстом в `Scan.error`.

Общий код между сканерами не выносится: клиент к control-api
(`control_client.py`) у каждого свой.

### 7.1. scanner-deepteam (динамическое тестирование)

`scanner/deepteam/app/` — FastAPI-обёртка над DeepTeam:

- `runner.py` — оркестрация фаз (см. §4), запуск в отдельном потоке,
  защита от повторного запуска.
- `target.py` — `model_callback` для DeepTeam: переводит каждый
  сгенерированный DeepTeam запрос в свежий диалог с тестируемым агентом
  (REST `api` или LangGraph `langgraph`), синхронно. Режим `api` — любой
  HTTP API по `api_config`: метод, URL, заголовки, тело `json`/`form`/`text`
  с плейсхолдерами `{{message}}` и `{{session_id}}`, путь к ответу в JSON
  (`response_field`, с отрицательными индексами), путь проверки готовности
  (`health_path`). Нет поля ответа или ошибка HTTP — ошибка кейса.
  Подстановка — в один проход: плейсхолдер внутри текста атаки не
  раскрывается.
  Описание полей — `docs/running-locally.md`, раздел «Режим REST API».
- `deepteam_runner.py` — сопоставляет имена уязвимостей и атак из UI с
  классами DeepTeam (есть синонимы, например
  `AgentIdentityTrustAbuse` → `AgentIdentityAbuse`), запускает `red_team`,
  стримит его вывод в журнал и преобразует `RTTestCase` в JSON результатов.
- Модель-судья (симулятор и оценка) — `LLMModel` из `Scan.config`.
- Кейс считается пройденным, если его score ниже порога 0.5;
  `overall_score` — доля пройденных кейсов.

### 7.2. scanner-promptfoo (анализ кода)

`scanner/promptfoo/app/` — FastAPI-обёртка над CLI `promptfoo code-scans`
(образ на Node 24 LTS, версия promptfoo зафиксирована в `Dockerfile`).
Агент не собирается и не запускается.

Фазы: **Инициализация** (скан, конфиг агента, параметры, наличие
`PROMPTFOO_API_KEY`) → **Клонирование** (`git clone --depth 1` ветки
`git_ref`, токен — как в launcher) → **Анализ кода** (`promptfoo code-scans
run --json`, heartbeat в журнал раз в 30 с, таймаут `SCAN_CODE_TIMEOUT`) →
**Сохранение результатов** → **Завершено**.

promptfoo сканирует только изменения между двумя коммитами, поэтому для
аудита всей ветки в клоне создаются два служебных коммита: пустой и с
деревом ветки (`git commit-tree`). Анализ выполняет облако Promptfoo: код
агента уходит к ним. Подробности, формат `Scan.results` и ограничения — в
[`code-scan-architecture.md`](code-scan-architecture.md).

## 8. Launcher

`POST /launch {scan_id}`:

1. читает `Scan` и связанный `AgentConfig`;
2. создаёт namespace `scan-<slug(session_id)>` и копирует туда CA-секрет;
3. если задан `env_example_path` — делает локальный shallow-clone и
   дозаполняет отсутствующие `env_vars` значениями по умолчанию из репо
   (заданные явно имеют приоритет);
4. собирает `dockerfile_path` через Kaniko (контекст — всегда корень репо);
5. запускает Pod (см. §3) и, если задан `api_port`, создаёт `NodePort`-сервис
   и прописывает доступный адрес в `api_config.url` /
   `langgraph_config.base_url`; те же поля возвращает в ответе как
   `agent_config_patch` — по ним сканер обращается к агенту своего скана;
6. сохраняет метаданные запуска в `Scan`.

Общий CA-секрет создаётся при первом `/launch`; одновременный первый
запуск двух сканов обрабатывается (409 — секрет уже создан параллельно).
Ветка и адрес репозитория попадают в shell-команду клонирования только
через `shlex.quote`.

`git_access_token` встраивается в clone-URL (`git_auth.py`), работает
только для HTTPS; известная утечка — токен может попасть в логи init-
контейнера при неудачном клоне (задокументировано, не исправлено).

`/stop/{scan_id}` удаляет namespace целиком (вызывает `scanner-deepteam`
в конце скана); `/status/{scan_id}` возвращает фазу Pod.

## 9. Библиотека знаний

`control-api/app/api/library.py` читает Markdown из `LIBRARY_DIR`
(по умолчанию `/library`, монтируется из папки `library/` репозитория):

- `GET /library/articles` — список метаданных (свежие сверху);
- `GET /library/articles/{slug}` — материал с телом.

Категория — имя верхнеуровневой папки (или `category` во frontmatter);
`title`/`summary`/`tags`/`date`/`source` берутся из YAML-frontmatter с
разумными fallback'ами. Файлы можно добавлять без пересборки. Доступ
ограничен корнем библиотеки (защита от path traversal).

## 10. Миграции базы

`control-api` применяет Alembic на старте
(`app/db.py::init_db` → `alembic upgrade head`). Ревизии —
`control-api/app/migrations/versions/`. Базовая ревизия `0001_baseline` —
замороженный снимок схемы на момент внедрения Alembic. Базы, созданные до
неё, автоматически помечаются ей (stamp), данные при этом сохраняются.
**Тома не удаляются.**

## 11. Известные ограничения и техдолг

- **Учётные данные в открытом виде.** `LLMModel.api_key`,
  `AgentConfig.git_access_token`, `AgentConfig.env_vars` хранятся без
  шифрования — осознанный техдолг MVP.
- **`git_access_token` в логах.** См. §8.
- **Нет автотестов.** Проверка — живая: поднять сервисы, прогнать HTTP/k8s
  сценарий, посмотреть `/events` и логи Pod'ов.
- **Синтетические атаки DeepTeam зависят от провайдера.** Часть моделей
  отклоняет генерацию атак по политике безопасности провайдера.
- **Анализ кода уходит в облако Promptfoo.** Модель анализа выбирает
  Promptfoo, `LLMModel` не участвует; нужен `PROMPTFOO_API_KEY`.
- **Перезапуск сканера посреди скана** прерывает скан: при старте сервис
  переводит его в `failed`, продолжить нельзя — нужно создать скан заново.

## 12. Легаси

Каталоги `generator/` и `interactor/` относятся к предыдущей архитектуре
(кампании, шаблоны, fuzz/tree-движки) и **не входят в `docker-compose.yml`**.
Контроллер-API больше не содержит их эндпоинтов. Считайте их неактивными;
актуальные сценарии — сканеры из `scanner/`.
