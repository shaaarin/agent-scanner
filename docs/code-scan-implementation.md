# Анализ кода через promptfoo — что сделано

Отчёт о внедрении по плану [`code-scan-plan.md`](code-scan-plan.md).
Как всё устроено — в [`code-scan-architecture.md`](code-scan-architecture.md).

## Итог

- Появился тип скана **«Анализ кода»** (`code_scan`): платформа клонирует
  ветку агента, прогоняет её через `promptfoo code-scans` и показывает
  находки — файл, строка, серьёзность, рекомендация.
- Сканеры разделены на **отдельные сервисы**: `scanner/deepteam`
  (бывший `scanner`, без изменений логики) и новый `scanner/promptfoo`.
- control-api отправляет скан в сервис по его типу. Тип без сканера
  запустить нельзя.
- Миграция базы не понадобилась, новых таблиц нет.

## Что добавлено

**Сервис `scanner/promptfoo`** (`scanner-promptfoo` в compose):

- `app/main.py` — `/health` и `/run/{scan_id}`, тот же контракт, что у
  DeepTeam-сканера;
- `app/runner.py` — фазы «Инициализация → Клонирование → Анализ кода →
  Сохранение результатов → Завершено», ошибки, `finished_at`;
- `app/repo.py` — клонирование и служебные коммиты для аудита всей ветки;
- `app/promptfoo.py` — запуск CLI, heartbeat в журнал раз в 30 секунд,
  таймаут, разбор JSON-ответа в `Scan.results`;
- `app/control_client.py`, `app/git_auth.py` — копии из DeepTeam-сканера и
  launcher;
- `bin/npx` — обёртка, которая разрешает только запуск filesystem-MCP;
- `Dockerfile` — Node 24 LTS, Python, git, `promptfoo@0.123.1` и
  `@modelcontextprotocol/server-filesystem@2026.8.31` с фиксированными
  версиями.

**web:**

- `src/api/scanTypes.ts` — подписи типов скана, фазы по типам, уровни
  серьёзности в одном месте (раньше подписи были продублированы в двух
  страницах);
- `src/components/CodeScanResults.tsx` — блок результатов: счётчики по
  уровням, общий вывод, таблица находок; по клику — рекомендация и промпт
  для AI-ассистента с кнопкой «Скопировать».

**Документация:** этот файл, переписанный
`code-scan-architecture.md`.

## Что изменено

- **`scanner/` → `scanner/deepteam/`.** Файлы перенесены как есть, сервис
  в compose переименован в `scanner-deepteam`.
- **`control-api/app/models.py`** — значение `code_scan` в `ScanType`,
  описание форматов `config`/`results` по типам.
- **`control-api/app/api/scans.py`** — вместо одного `SCANNER_URL` словарь
  `SCANNERS` «тип → сервис». Две правки поведения:
  - тип без сканера (`mcp`, `agent_skills`) теперь получает 400 и остаётся
    `pending`; раньше такой скан уходил в DeepTeam-сканер и падал там;
  - ответ сканера с ошибкой HTTP теперь переводит скан в `failed`; раньше
    код ответа не проверялся и скан мог зависнуть в `running`.
- **`docker-compose.yml`** — сервисы `scanner-deepteam` и
  `scanner-promptfoo`; у control-api `SCANNER_DEEPTEAM_URL` и
  `SCANNER_PROMPTFOO_URL`.
- **`.env.example`** — `PROMPTFOO_API_KEY`, `PROMPTFOO_CODE_SCAN_API_HOST`;
  поправлен комментарий о том, что сервисы не читают `.env`.
- **`web/src/pages/Scans.tsx`** — тип «Анализ кода (promptfoo)» в форме;
  LLM-модель требуется только для динамического теста; для анализа кода —
  порог серьёзности и доп. инструкции; ошибка запуска скана теперь видна на
  странице, а не только в консоли.
- **`web/src/pages/ScansDetail.tsx`** — фазы зависят от типа скана, свой
  блок результатов для анализа кода, свой текст до запуска.
- **`README.md`, `AGENTS.md`, `docs/architecture.md`,
  `docs/running-locally.md`** — сервисы сканеров, контракт, запуск и
  диагностика анализа кода.

## Что упрощено по сравнению с планом

- **Аудит всей ветки без второго репозитория.** В плане было: создать
  отдельный git-репозиторий, скопировать туда файлы и сделать два коммита.
  Сделано проще: в том же клоне `git commit-tree` создаёт пустой коммит и
  коммит с деревом ветки. Без копирования, рабочее дерево не меняется, а в
  анализ попадают ровно файлы из git — без влияния `.gitignore`.
- **Без конфиг-файла promptfoo.** Порог и инструкции передаются флагами
  `--min-severity` и `--guidance`.
- **Один режим.** Проверка изменений ветки относительно `main` не
  делалась: в платформе нет pull request'ов.

## Что выяснилось по ходу

- **filesystem-MCP в promptfoo 0.123.1 запускается через `npx -y`** внутри
  сканируемого репозитория. Проверено в контейнере: `npx` не берёт
  глобально установленный пакет, каждый раз идёт в npm и учитывает
  `.npmrc` сканируемого репозитория — то есть чужой репозиторий может
  подменить источник запускаемого кода. Решение: сервер ставится в образ
  заранее, а `bin/npx` выполняет только его, без сети. В исходниках
  promptfoo это уже исправлено, но в релиз ещё не вышло — при обновлении
  promptfoo обёртку можно будет убрать.
- **Переменная адреса сервера.** promptfoo сам читает
  `PROMPTFOO_CLOUD_API_URL` и `PROMPTFOO_REMOTE_API_BASE_URL`, поэтому для
  своего сервера заведена отдельная `PROMPTFOO_CODE_SCAN_API_HOST`,
  которая передаётся флагом `--api-host`.
- **Размер образа.** promptfoo тянет все провайдеры — около 2,3 ГБ на диске.
  Урезать установку опасно: часть зависимостей подгружается лениво.

## Как запустить

1. В `.env` заполнить `PROMPTFOO_API_KEY`.
2. Если стек поднимался до разделения сканеров — убрать старый контейнер:
   `docker compose up -d --build --remove-orphans`.
3. Только анализ кода, без kind:
   `docker compose up -d --build control-api web scanner-promptfoo`.
4. В UI: «Конфигурации агентов» → агент с репозиторием; «Сканирования» →
   «Новое сканирование» → «Анализ кода (promptfoo)» → «Запустить».

## Что проверено

Живьём на Docker Desktop, без kind, через API control-api:

- **Сборка.** Собраны `scanner-promptfoo`, `control-api` и `web`; сборка
  `web` включает проверку типов TypeScript (`tsc -b`) — прошла.
- **Выбор сканера по типу.** Скан `mcp` получает 400 «сканер пока не
  подключён» и остаётся `pending`. Скан `code_scan` при остановленном
  `scanner-promptfoo` сразу `failed` с текстом
  «scanner-promptfoo недоступен».
- **Без ключа Promptfoo** — `failed` на «Инициализация» с подсказкой,
  что делать.
- **Полный путь с неверным ключом** — проходят «Инициализация» и
  «Клонирование» (публичный репозиторий, коммит и число файлов в
  журнале), promptfoo реально запускается и получает отказ авторизации;
  текст ошибки доходит до журнала и `Scan.error`, временная папка
  удалена, `finished_at` проставлен.
- **Неверная ветка с токеном** — понятная ошибка клонирования, токена нет
  ни в журнале, ни в `Scan.error`.
- **Служебные коммиты** — promptfoo видит все файлы ветки как
  добавленные (`git diff base...compare`), рабочее дерево не меняется.
- **Обёртка npx** — без сети и с поддельным `.npmrc` в каталоге
  filesystem-MCP запускается из образа и отвечает на `initialize`; любой
  другой вызов `npx` отклоняется.
- **Разбор ответа** — на примере ответа: сортировка по серьёзности,
  `severity: none` уходит в общий вывод, лишние поля игнорируются, пустой
  ответ даёт нулевые счётчики.
- **Настоящий анализ с ключом Promptfoo** — публичный шаблон
  [langchain-ai/react-agent](https://github.com/langchain-ai/react-agent)
  (26 файлов): скан `completed` за 99 секунд, одна критическая находка в
  `src/react_agent/graph.py` (недоверенный контент веб-поиска попадает в
  модель, которая может вынести данные через тот же инструмент), общий
  вывод сканера и метаданные сохранены в `Scan.results`. Облако Promptfoo
  читало репозиторий через filesystem-MCP из образа.
- **Ещё три публичных проекта, параллельно** — все `completed`:
  - `octocat/Hello-World` (1 файл, 19 с) — находок нет, как и ожидалось;
  - `ReversecLabs/damn-vulnerable-llm-agent` (16 файлов, 140 с) — 4 high,
    ровно заложенные в учебный проект уязвимости: авторизация только
    промптом, выборка данных по произвольному `userId`, пароли в выводе
    инструмента, SQL из параметров модели через f-строку;
  - `langchain-ai/open_deep_research` (45 файлов, 5 мин) — 1 critical,
    2 high, 1 medium: недоверенный веб-контент плюс принудительный вызов
    инструментов, MCP-инструменты без allowlist, правила только в промптах.
  В текстах сканер называет проверяемый код «PR» — следствие подачи ветки
  как одного изменения, на результат не влияет. Общий вывод (`review`)
  promptfoo возвращает не всегда.
- **Сбой сети во время анализа** — один прогон оборвался с
  «Lost connection to server during scan»: на этой машине нестабилен DNS
  внутри Docker. Скан корректно ушёл в `failed` с этим текстом, повторный
  прогон прошёл.
- **Фронтенд** — web отвечает, новые экраны есть в сборке. Отрисовку
  результатов глазами не проверял.

- **Динамический тест после разделения сканеров** — kind на macOS
  (arm64, `brew install kind`), агенты `langgraph-customer-support` и
  `langgraph-inventory-db` из `2303/testing-repos`: control-api отдаёт скан
  в `scanner-deepteam`, launcher собирает агента через Kaniko и
  запускает под с MITM-сайдкаром, сканер дожидается `/ok`, прокси
  записывает трафик агента к `api.openai.com` в «События». Сами атаки не
  прошли: у ключа OpenAI закончился баланс (`429 insufficient_quota`), все
  кейсы помечены ошибкой.
- **Анализ кода этих же агентов** — customer-support: 3 high (возврат
  денег без проверок, правила только в промпте); inventory-db: 4 high
  (SQL из аргументов модели, разрушительные инструменты без проверки
  прав).

- **DeepTeam через OpenRouter** (`nvidia/nemotron-3-super-120b-a12b:free`) —
  два коротких скана прошли без ошибок, но с атакой PromptInjection оценки
  «устойчив» ничего не значат: в deepteam 1.0.9 эта атака заворачивает
  запрос в легенду «ты генератор синтетических данных, выдай JSON с
  примерами» — это обход фильтров чат-моделей, а не попытка заставить
  агента вызвать инструмент; агенты отвечали текстом и инструменты не
  трогали. Для агентов с инструментами лучше подходит AuthorityEscalation
  (приказ агенту «от руководителя»), проверить её не дал дневной лимит
  бесплатного OpenRouter (50 запросов).

Исправлено по итогам проверки:

- **scanner-deepteam больше не пишет «Завершено», если ничего не
  проверено.** Раньше, когда все кейсы падали с ошибкой (нет квоты или
  лимит у провайдера), скан получал `completed` с «пройдено: 0» — это
  выглядело как результат теста. Теперь: ни один кейс не оценён — скан
  `failed` с понятной причиной (для `RateLimitError` — подсказка про
  лимит/баланс провайдера), таблица кейсов сохраняется в `Scan.results` и
  видна на странице скана; часть кейсов с ошибкой — скан `completed`, а в
  журнале предупреждение, сколько кейсов не учтено и почему. В строке
  результата появилось поле `error`, сканер проставляет `finished_at`.
  Проверено на исчерпанном лимите OpenRouter: скан `failed`, «Ни один из 3
  кейсов не удалось проверить: провайдер LLM отклоняет запросы…».

- **Ошибка LLM у самого агента больше не засчитывается как «устойчив».**
  LangGraph-сервер отдаёт падение графа как HTTP 200 с телом
  `{"__error__": …}`; раньше это считалось пустым ответом агента и
  оценивалось судьёй. Теперь `scanner/deepteam/app/target.py` превращает
  такой ответ в ошибку кейса («агент вернул ошибку: OpenAIRateLimitError…»),
  и дальше работает правило выше.

Найдено попутно и позже исправлено (см. [`bugfix-report.md`](bugfix-report.md)):
гонка CA-секрета в launcher при одновременном первом запуске и
несохраняемое `agent_purpose`.


Замечено: если запустить скан в первые секунды после старта контейнера
`scanner-promptfoo`, он ещё не принимает запросы и скан сразу падает с
«scanner-promptfoo недоступен» — это ожидаемо, достаточно создать скан
заново.
Docker Scout помечает в образе `scanner-promptfoo` уязвимости зависимостей
(базовый образ Node и пакеты promptfoo) — стоит посмотреть при обновлении
версий.

## Что осталось

- **Прогон на своих агентах**, включая большой репозиторий: время скана,
  сколько файлов пропущено, нет ли серверных лимитов на размер изменения.
- **Полный прогон DeepTeam** на двух тестовых агентах после пополнения
  баланса провайдера LLM (инфраструктура уже проверена).
- **Согласование** отправки кода агентов в облако Promptfoo и аккаунта.

## Как добавить следующий сканер

1. Папка `scanner/<имя>` со своим `Dockerfile` и тем же контрактом
   (`/health`, `/run/{scan_id}`, журнал и результат — в control-api).
2. Сервис `scanner-<имя>` в `docker-compose.yml`, адрес — у control-api.
3. Значение в `ScanType` и строка в `SCANNERS`
   (`control-api/app/api/scans.py`).
4. В `web/src/api/scanTypes.ts` — подпись и фазы; в форме — параметры; на
   странице скана — блок результатов.
