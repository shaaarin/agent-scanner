# Отчёты сканеров, сводка актива, выгрузки и усиление инъекционных сканеров

Описание изменений по четырём задачам. Формат отчёта и шкала оценки —
[`reports.md`](reports.md), устройство — [`architecture.md`](architecture.md)
§7.8–7.9.

## 1. Единый формат отчётов сканеров

**Было:** четыре разных формата `Scan.results`. DeepTeam и PyRIT писали строки
кейсов, Promptfoo и Semgrep — находки с файлом и строкой, косвенные инъекции и
утечка промпта — прогоны с вердиктом, MCP — находки движков. Сравнить сканеры
между собой было нельзя, UI разбирал каждый формат своим компонентом.

**Стало:** сканеры по-прежнему пишут свой нативный формат, а control-api
приводит его к одному виду **при чтении** — `control-api/app/reports.py`,
эндпоинт `GET /scans/{id}/report`:

- **единые метрики** — `checks_passed/failed/errored/skipped`,
  `resistance_rate`, `attack_success_rate`, `findings_total`, `by_severity`;
- **единый формат находки** — серьёзность, правило, локация (файл:строки),
  основание, рекомендация, а для динамики — диалог атаки;
- **оценка устойчивости** — Защищён / Частично защищён / Небезопасен / Нет
  данных: худшая из оценки по серьёзности находок и по доле успешных атак.

Миграций не потребовалось, сканы, снятые раньше, получают новый формат без
перезапуска. Знание о формате конкретного сканера живёт в одном месте
(`_NORMALIZERS`). UI рендерит общий компонент `web/src/components/ScanReport.tsx`;
родной отчёт сканера остался под раскрывающимся блоком «Отчёт сканера как есть».

## 2. Сводка-дашборд в карточке актива

Добавлены `GET /assets/{kind}/{id}/summary` и
`web/src/components/AssetSummary.tsx`: оценка устойчивости актива, число находок
и разбивка по серьёзности, счётчики сканирований по статусам, дата последнего
сканирования и таблица по типам сканирований со ссылками на сканы.

Находки и оценка считаются по **последнему завершённому скану каждого типа** —
иначе повторные прогоны одного сканера удваивали бы находки. Оценка актива —
худшая среди типов; «Нет данных» оценку не ухудшает.

## 3. Выгрузка результатов сканирования

| Эндпоинт | Для чего | Формат |
|---|---|---|
| `GET /scans/{id}/report` | единый отчёт | JSON |
| `GET /scans/{id}/export/sarif` | статика и MCP | SARIF 2.1.0 |
| `GET /scans/{id}/export/attacks` | динамика | JSON с диалогами успешных атак |

- **SARIF** (`control-api/app/sarif.py`) — понимают GitHub code scanning,
  GitLab и IDE. Promptfoo не возвращает идентификаторов правил, поэтому
  `ruleId` выводится из текста находки: иначе разные проблемы схлопывались бы в
  один алерт.
- **Диалоги атак** — только успешные: атакующие промпты и ответы агента. Для
  инъекций берутся прогоны из базы (подложенный payload помечен `injected`) и
  перехваченный запрос к LLM с реальной подменой.
- Выгрузка не того вида отклоняется с 422 и подсказкой. Кнопки выгрузки — в
  блоке отчёта на странице скана.

Чтобы диалоги вообще сохранялись, доработаны сканеры: DeepTeam пишет
`input`/`actual_output`/`turns`/`cvss_score` из `RTTestCase`, PyRIT записывает
диалог в своей цели `AgentPromptTarget` (`begin_capture`/`end_capture`).

## 4. Усиление сканеров инъекций и утечки системного промпта

**Было:** 5 статических инъекций и 6 атакующих промптов — проверка узкая: агент
может устоять перед прямой формулировкой, но выполнить то же в другой обёртке.

| | было | стало |
|---|---|---|
| косвенные инъекции | 5 payload'ов | 14 payload'ов × 10 мутаторов = **140** вариантов |
| утечка системного промпта | 6 промптов | 15 промптов × 10 мутаторов = **150** вариантов |

- **Мутаторы** (`app/mutators.py`, свой у каждого сканера) — обёртки вокруг
  базового текста: поддельный системный тег, служебное поле JSON, выделение
  markdown, комментарий в коде, давление срочностью, повтор с усилением,
  base64, невидимые разделители (U+200B), leetspeak. Детерминированы: одна
  комбинация всегда даёт один текст, поэтому прогоны воспроизводимы и сравнимы.
  Идея повторяет конвертеры PyRIT, но реализована локально — сканер
  самодостаточен, а конвертеры PyRIT покрывает отдельный `scanner-pyrit`.
- **Контрольная метка при мутации не меняется** — на ней держится
  детектирование. Исключение `base64`: кодируется весь текст вместе с меткой,
  это осознанно более сложный вариант (агент должен сам декодировать).
- **Внешние наборы** — каталоги `payloads/indirect/` и `payloads/sysleak/`
  монтируются read-only (`EXTRA_PAYLOADS_DIR`) и читаются на лету: свой или
  сторонний корпус подключается **без пересборки образа**, совпадающее `name`
  переопределяет встроенный payload.
- **Больше точек инъекции** (`occurrences`, только `indirect_injection`) —
  фаззить не только первый вызов каждого инструмента, но и последующие.

Параметры `mutators` и `occurrences` сканеры отдают в `GET /schema`, поэтому в
форме создания скана они появляются сами — фронтенд не правился.

Генерацию payload'ов моделью не делали: статика детерминирована и
воспроизводима, а покрытие расширено мутаторами и внешними наборами.

## Исправлено по ходу

- Если **все** кейсы динамики падали с ошибкой (лимит провайдера), оценка
  выходила «Защищён» — теперь «Нет данных»: проверить ничего не удалось.
- У скана, упавшего с частичными результатами, терялись метрики.
- `leetspeak` не срабатывал на заглавных буквах.

## Проверено

Автотестов в проекте нет, проверка живая: отчёт и шкала — на сканах всех 7
типов, включая скан с ошибкой, ещё не запущенный и повторный скан того же типа;
SARIF — валидатором по официальной схеме SARIF 2.1.0; диалоги — для всех
четырёх динамических сканеров, включая многораундовые PyRIT; мутаторы —
сохранность метки во всех 10 обёртках и сборка всех 140/150 вариантов;
подключение и переопределение внешнего набора на лету; новые поля формы — через
`GET /scanners`. Фронтенд собирается строгим `tsc`; отрисовку в браузере не
проверяли.

## Ограничения

- Оценка устойчивости — эвристика по серьёзности находок и доле успешных атак,
  а не формальная модель риска; пороги (ASR ≥ 30% → «Небезопасен») заданы в
  `reports.py`.
- Число прогонов растёт как «задачи × точки × варианты × повторы», все вызовы
  идут в реальный провайдер — `max_trials` остаётся предохранителем.
