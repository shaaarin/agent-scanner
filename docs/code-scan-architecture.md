# Анализ кода агента через promptfoo — архитектура

## Суть

Сейчас платформа проверяет агента только в работе: собирает, запускает в
kind и атакует через DeepTeam. Добавляем второй вид проверки — анализ
исходного кода агента сканером `promptfoo code-scans`. Он читает код и
находит места, где возможны prompt injection, утечка персональных данных,
лишние полномочия у модели, опасные инструменты. По каждой проблеме
выдаёт файл, строку, серьёзность и рекомендацию.

Для пользователя это новый тип скана «Анализ кода». Агент выбирается тот
же, что и для динамического теста, всё остальное — как у обычного скана:
кнопка запуска, живой журнал, результаты на странице скана.

Заодно меняем принцип: **каждый сканер — отдельный сервис**. DeepTeam и
promptfoo живут в своих контейнерах, следующие сканеры (MCP, Agent Skills)
добавляются так же.

## Что важно знать о promptfoo code-scans

- Это команда CLI `promptfoo code-scans run`, нужен Node 22.22 или новее.
  Версию фиксируем, как это делает официальный GitHub Action promptfoo,
  и ставим с `--ignore-scripts`.
- Анализ делает не наша модель, а облако Promptfoo. CLI отправляет код на
  их сервер, а серверный агент при необходимости дочитывает остальные
  файлы репозитория через локальный MCP, который CLI поднимает сам.
- Нужен ключ `PROMPTFOO_API_KEY`. Своя установка сервера есть только в
  платной Enterprise-версии, адрес меняется флагом `--api-host`.
- Сканер смотрит не на весь репозиторий, а на изменения между двумя
  коммитами — он сделан под проверку pull request'ов.
- Файлы больше 500 KB, сборочные каталоги, lock-файлы и бинарники он
  пропускает сам.
- Порог серьёзности и дополнительные инструкции передаются флагами
  `--min-severity` и `--guidance`, отдельный конфиг-файл не нужен.
- С флагом `--json` результат приходит одним JSON в конце работы, до этого
  CLI молчит. Скан длится от нескольких минут до 20+ на больших репо.
- Код возврата 0 значит, что скан прошёл, даже если проблемы найдены.
  Ненулевой код — ошибка самого скана.

## Сервисы сканеров

В репозитории сканеры лежат в одной папке, каждый в своей подпапке:

- `scanner/deepteam` — нынешний `scanner`, переносится как есть.
  Динамическое тестирование, ходит в launcher и в сеть kind.
- `scanner/promptfoo` — новый. Анализ кода, kind и launcher не нужны.
- дальше по тому же принципу: `scanner/mcp`, `scanner/agent-skills`.

Каждый сканер — отдельный сервис в `docker-compose.yml`
(`scanner-deepteam`, `scanner-promptfoo`) со своим образом и своими
зависимостями. Так DeepTeam не тянет в образ Node, а promptfoo — Python-
зависимости DeepTeam; сканеры обновляются и падают независимо.

У всех сканеров одинаковый контракт с control-api, тот, что уже есть у
`scanner`:

- `GET /health`;
- `POST /run/{scan_id}` — отвечает сразу, работа идёт в фоне;
- фазы, журнал и результаты сканер пишет в control-api через
  `PATCH /scans/{id}` и `POST /scans/{id}/logs`.

control-api выбирает сервис по типу скана: `deep_team` — в
`scanner-deepteam`, `code_scan` — в `scanner-promptfoo`. Адреса задаются
переменными окружения. Если для типа сканер не настроен, запуск
отклоняется с понятной ошибкой, а не уходит в чужой сервис.

Клиент к control-api (`control_client.py`, ~40 строк) каждый сканер
держит у себя копией. Общий пакет выделим, если сканеров станет больше
двух-трёх и копии начнут расходиться.

## Как проходит анализ кода

1. Пользователь создаёт скан типа `code_scan` и нажимает «Запустить».
   control-api, как и сейчас, переводит его в `running` и вызывает
   `scanner-promptfoo`.
2. **Инициализация.** Сканер читает скан и конфигурацию агента,
   проверяет, что задан ключ Promptfoo.
3. **Клонирование.** Сканер клонирует ветку `git_ref` из
   `git_repo_url` во временную папку. Для приватных репозиториев токен
   встраивается в адрес так же, как в launcher. В журнал и в текст ошибки
   адрес попадает без токена.
4. **Анализ кода.** Сканер запускает promptfoo и ждёт результат. Раз в
   полминуты пишет в журнал, что анализ идёт и сколько прошло времени.
   Если анализ не уложился в отведённое время, процесс останавливается и
   скан завершается ошибкой.
5. **Сохранение результатов.** Сканер разбирает ответ, сохраняет находки
   в `Scan.results` и переводит скан в `completed`. Временная папка
   удаляется в любом случае.

Любая ошибка — неверный токен, нет ключа, сбой Promptfoo, таймаут —
обрабатывается как в DeepTeam-сканере: строка в журнале, статус `failed`,
текст в `Scan.error`.

## Как сканируем весь репозиторий

Платформа проверяет агента целиком, а promptfoo умеет проверять только
изменения. Поэтому весь код агента подаётся ему как одно большое
изменение.

После клонирования сканер создаёт рядом новый локальный git-репозиторий
с пустым первым коммитом, копирует туда файлы агента и делает второй
коммит. Promptfoo запускается со сравнением «пустой коммит → коммит с
кодом» и видит каждый файл как добавленный. Исходный `.gitignore`
репозитория при этом соблюдается.

Проверку отдельной ветки относительно `main` в первую версию не берём: в
платформе нет понятия pull request, агент описывается одной веткой.

## Данные

Новых таблиц и миграций нет. Колонка `scan.type` в базе строковая, поэтому
достаточно добавить значение `code_scan` в `ScanType`.

В `Scan.config` для анализа кода два необязательных поля: минимальная
серьёзность (`min_severity`, по умолчанию `medium`) и дополнительные
инструкции сканеру (`guidance`). Модель-судья для этого типа не нужна.

В `Scan.results` сохраняются:

- общий вывод сканера;
- количество находок по каждому уровню серьёзности;
- список находок, отсортированный от критичных к низким: файл, строка,
  уровень, описание, рекомендация, готовый промпт для AI-ассистента;
- коммит, который проверяли, версия promptfoo и длительность скана.

Комментарии сканера без уровня серьёзности идут в общий вывод, а не в
список находок. Незнакомые поля из ответа promptfoo игнорируются:
формат CLI ещё может меняться. Результаты DeepTeam остаются в прежнем
формате, страница скана различает их по типу.

## Что меняется в коде

**scanner/deepteam.** Перенос нынешнего `scanner/` в подпапку без
изменений логики. В `docker-compose.yml` сервис `scanner` становится
`scanner-deepteam`, сеть kind и `LAUNCHER_URL` остаются.

**scanner/promptfoo (новый).**

- `app/main.py` — `/health` и `/run/{scan_id}`, как у DeepTeam-сканера.
- `app/runner.py` — фазы, обработка ошибок, защита от повторного запуска.
- `app/code_scan.py` — клонирование, подготовка репозитория, запуск
  promptfoo, разбор ответа.
- `app/control_client.py` — копия из DeepTeam-сканера.
- `app/git_auth.py` — копия `launcher/app/git_auth.py`.
- `Dockerfile` — Node 22, Python, git; promptfoo фиксированной версии.

**control-api.**

- `app/models.py` — значение `code_scan` в `ScanType`.
- `app/api/scans.py` — вместо одного `SCANNER_URL` адрес сканера по типу
  скана (`SCANNER_DEEPTEAM_URL`, `SCANNER_PROMPTFOO_URL`). Текст ошибки
  «scanner недоступен» — с именем конкретного сервиса.
- Токен репозитория сканер получает из существующего
  `GET /agent-configs/{id}`, новых эндпоинтов нет.

**web.**

- Форма создания скана: тип «Анализ кода», для него не требуется
  LLM-модель, вместо уязвимостей и атак — порог серьёзности и
  дополнительные инструкции.
- Страница скана: свой список фаз для анализа кода (сейчас фазы
  захардкожены под DeepTeam) и свой блок результатов — счётчики по
  уровням, общий вывод и таблица находок с раскрытием рекомендации.
- Весь текст — на русском.

## Окружение

`docker-compose.yml`:

- `scanner-deepteam` — как нынешний `scanner`, сборка из
  `./scanner/deepteam`;
- `scanner-promptfoo` — сборка из `./scanner/promptfoo`, только
  default-сеть, без опубликованного порта; переменные
  `CONTROL_API_URL`, `PROMPTFOO_API_KEY` из `.env`, необязательный
  `PROMPTFOO_API_HOST`, `PROMPTFOO_DISABLE_TELEMETRY=1` и таймаут
  `SCAN_CODE_TIMEOUT` (по умолчанию 30 минут);
- у control-api вместо `SCANNER_URL` — `SCANNER_DEEPTEAM_URL` и
  `SCANNER_PROMPTFOO_URL`.

В `.env.example` добавляется ключ Promptfoo. Комментарий в этом файле о
том, что сервисы `.env` не читают, нужно поправить: ключ Promptfoo
читается именно оттуда.

Сервису promptfoo нужен исходящий доступ к `api.promptfoo.app` и к
git-хостингу агента.

## Безопасность и ограничения

- Код агента уходит в облако Promptfoo. Для закрытых репозиториев это
  нужно согласовать отдельно.
- Токен репозитория и ключ Promptfoo не попадают в журнал. Хранение
  токена в открытом виде — существующий принятый техдолг.
- Код агента не исполняется, только читается.
- На больших репозиториях скан идёт долго, часть файлов promptfoo
  пропускает по размеру. Как сервер Promptfoo ведёт себя на очень большом
  изменении, нужно проверить на реальном агенте.
- Повторный скан того же кода может дать немного другие находки — как и
  у DeepTeam.
- Если сканер перезапустить посреди скана, скан останется в `running`.
  Это уже так для DeepTeam, отдельно не решаем.

## Проверка

Автотестов в проекте нет, проверяем вживую:

- после переноса DeepTeam-сканера динамический тест работает как раньше;
- агент с заведомой уязвимостью, например ввод пользователя без обработки
  уходит в системный промпт, — анализ кода должен её найти;
- агент без LLM-кода — скан завершается без находок;
- неверный токен или ветка — понятная ошибка, токена в журнале нет;
- нет ключа Promptfoo — ошибка на инициализации;
- динамический тест и анализ кода одновременно не мешают друг другу.

После внедрения обновляются `docs/architecture.md`,
`docs/running-locally.md` и `AGENTS.md` — таблица сервисов и описание
сканеров.
