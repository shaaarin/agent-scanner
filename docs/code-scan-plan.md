# План: анализ кода агента через promptfoo

Подробности — в [`code-scan-architecture.md`](code-scan-architecture.md),
что сделано — в [`code-scan-implementation.md`](code-scan-implementation.md).

## Что делаем

Добавляем тип скана «Анализ кода». Платформа клонирует репозиторий
агента, прогоняет его через `promptfoo code-scans` и показывает найденные
проблемы: файл, строка, серьёзность, как исправить. Агента для этого не
собираем и не запускаем.

## Решение

- Новый тип скана `code_scan` рядом с `deep_team`.
- Каждый сканер — отдельный сервис: `scanner/deepteam`,
  `scanner/promptfoo`, дальше `scanner/mcp` и т.д.
- control-api отправляет скан в нужный сервис по его типу.
- Агент берётся из существующей конфигурации: репозиторий, ветка, токен.
- Миграция базы не нужна.
- promptfoo проверяет только изменения, поэтому всю ветку подаём ему как
  одно изменение: в клоне создаются пустой коммит и коммит с кодом ветки.

## Этапы

1. **Разделение сканеров** — сделано. `scanner/` перенесён в
   `scanner/deepteam`, сервис — `scanner-deepteam`, control-api выбирает
   сканер по типу скана.
2. **scanner/promptfoo** — сделано. Клонирование, запуск promptfoo,
   сохранение результатов; образ на Node 24 с фиксированными версиями
   promptfoo и filesystem-MCP.
3. **control-api и окружение** — сделано. `code_scan` в `ScanType`, сервис
   в `docker-compose.yml`, `PROMPTFOO_API_KEY` в `.env.example`.
4. **web** — сделано. Тип «Анализ кода» в форме, свои фазы и таблица
   находок на странице скана.
5. **Проверка и документация** — документация обновлена, настоящий анализ
   с ключом Promptfoo прошёл на публичном агенте. Осталось: прогон на своих
   агентах, включая большой репозиторий, и динамический тест на kind после
   переименования сервиса.

## Что согласовать

- Анализ выполняет облако Promptfoo, код агента уходит к ним.
- Нужен аккаунт и API-ключ Promptfoo, а также понимание лимитов тарифа.
