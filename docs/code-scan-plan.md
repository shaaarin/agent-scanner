# План: анализ кода агента через promptfoo

Подробности — в [`code-scan-architecture.md`](code-scan-architecture.md).

## Что делаем

Добавляем тип скана «Анализ кода». Платформа клонирует репозиторий
агента, прогоняет его через `promptfoo code-scans` и показывает найденные
проблемы: файл, строка, серьёзность, как исправить. Агента для этого не
собираем и не запускаем.

## Решение

- Новый тип скана `code_scan` рядом с `deep_team`.
- Каждый сканер — отдельный сервис: `scanner/deepteam`,
  `scanner/promptfoo`, дальше `scanner/mcp` и т.д.
- control-api отправляет скан в нужный сервис по его типу.
- Агент берётся из существующей конфигурации: репозиторий, ветка, токен.
- Миграция базы не нужна.
- promptfoo проверяет только изменения, поэтому весь код агента подаём
  ему как одно изменение относительно пустого коммита.

## Этапы

1. **Разделение сканеров.** Перенести нынешний `scanner/` в
   `scanner/deepteam`, сервис в compose — `scanner-deepteam`. В
   control-api выбирать адрес сканера по типу скана. Убедиться, что
   динамический тест работает как раньше.
2. **scanner/promptfoo.** Новый сервис с тем же контрактом
   (`/health`, `/run/{scan_id}`): клонирование, запуск promptfoo,
   сохранение результатов. Образ с Node 22, git и promptfoo
   фиксированной версии.
3. **control-api и окружение.** Значение `code_scan` в `ScanType`. Сервис
   `scanner-promptfoo` в `docker-compose.yml`, ключ `PROMPTFOO_API_KEY` в
   `.env.example`. Проверить скан через API.
4. **web.** Тип «Анализ кода» в форме создания, свои фазы и таблица
   находок на странице скана.
5. **Проверка и документация.** Прогнать на 2–3 реальных агентах, включая
   большой репозиторий. Обновить `architecture.md`, `running-locally.md`
   и `AGENTS.md`.

## Что согласовать

- Анализ выполняет облако Promptfoo, код агента уходит к ним.
- Нужен аккаунт и API-ключ Promptfoo, а также понимание лимитов тарифа.
