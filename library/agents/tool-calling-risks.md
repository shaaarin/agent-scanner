# Риски вызова инструментов агентом

## Суть

Давая агенту инструменты, вы даёте модели возможность влиять на внешний мир.
Ошибка в описании инструмента, отсутствие проверок на стороне сервиса или
излишняя автономность превращают безобидную подсказку в нежелательное действие.

## Типовые проблемы

- **Чрезмерные полномочия.** Инструмент делает больше, чем нужно задаче:
  `issue_refund` без лимита, `run_shell` без ограничения команд, доступ ко
  всем записям вместо своих.
- **Подмена аргументов.** Значения из пользовательского текста попадают в
  аргументы инструмента без валидации: SQL, URL (SSRF), пути файлов, HTML (XSS).
- **Обход бизнес-правил.** Агент пропускает обязательный шаг, потому что модель
  убедили, что «проверка уже пройдена».
- **Неавторизованный вызов.** Инъекция заставляет вызвать инструмент, который
  для этой роли недоступен.

## Что проверять

1. Есть ли валидация аргументов на стороне самого инструмента, а не только в промпте.
2. Можно ли заставить агента вызвать инструмент, который он не должен
   использовать в этом сценарии.
3. Можно ли вложить управляемые данные в аргумент, влияющий на запрос к БД,
   сеть или файловую систему.
4. Есть ли подтверждение для необратимых действий (платежи, удаление, отправка).

## Принцип

Никогда не полагайтесь на промпт как на границу безопасности. Авторизацию и
валидацию делает код, а не модель.
