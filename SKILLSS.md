# SKILLSS — архитектурные решения по модулю анализа Agent Skills

Здесь записываются **все** архитектурные решения по модулю «анализ безопасности навыков (Agent Skills) LLM-агентов» (тип скана `agent_skills`, сервис `scanner-skills`). Что решили, почему и что из этого следует. Сюда же — открытые вопросы и принятые риски.

Правила ведения:
- Решение получает номер `D-NN` и не удаляется. Если передумали — новое решение со ссылкой «заменяет D-NN», а у старого статус `заменено`.
- Статусы решений: `принято` (согласовано с Максом/лидом), `предложено` (ждёт ответа), `заменено`.
- Риски — `R-NN`, статусы: `открыт`, `принят` (живём с ним осознанно), `закрыт` (решено, ссылка на `D-NN`).
- Подробный разбор движков и прогон на корпусе — в `docs/agent-skills-scanning-plan.md`. Этот файл — короткий реестр решений.

## 2. Схема

> **Частично устарело после master `90ee1a4`.** Шаги 2.2–2.3 (загрузка в `/skill-archives`, создание скана с `archive_id`) заменены активами: архив загружается в `SkillAsset`, скан создаётся из карточки актива, сканер берёт архив из `GET /skill-assets/{id}/content` (D-38…D-40). Схему перепишу после ответов на R-27…R-30.

### 2.1 Кто участвует

| Компонент | Что делает в этом модуле |
|---|---|
| `web` | Форма: пользователь загружает архив, выбирает (или не выбирает) LLM-модель, создаёт и запускает скан. Страница скана: фазы, журнал, отчёт |
| `control-api` | Принимает архив и делает лёгкую проверку, хранит файл и запись `SkillArchive`, хранит `Scan`, по кнопке «Запустить» вызывает `scanner-skills`. Отдаёт сканеру архив и `LLMModel` |
| `scanner-skills` | Забирает архив, безопасно распаковывает, запускает движки, собирает единый отчёт, пишет фазы/журнал/результат обратно в control-api |
| Cisco skill-scanner, SkillSpector | CLI-программы внутри образа `scanner-skills`, каждая в своём venv. Получают папку со скиллом, возвращают JSON |
| LLM-провайдер | Только если выбрана модель: к нему ходят движки, а не наш код |

kind, launcher, proxy в этом модуле не участвуют: агент не собирается и не запускается.

### 2.2 Шаг 1 — загрузка архива (до создания скана)

```
Пользователь            web                         control-api                       диск control-api
    │  выбирает файл     │                               │                                  │
    │───────────────────▶│ POST /skill-archives          │                                  │
    │                    │ (multipart: file)             │                                  │
    │                    │──────────────────────────────▶│ 1. размер ≤ лимита (читаем поток │
    │                    │                               │    с ограничением, не целиком)   │
    │                    │                               │ 2. это zip? (или SKILL.md →      │
    │                    │                               │    заворачиваем в zip)           │
    │                    │                               │ 3. оглавление: число записей,    │
    │                    │                               │    сумма размеров, сжатие,       │
    │                    │                               │    пути с .. / абсолютные        │
    │                    │                               │ 4. есть хотя бы один SKILL.md    │
    │                    │                               │ 5. ≤ 10 скиллов (D-13)           │
    │                    │                               │──── сохранить <sha256>.zip ─────▶│
    │                    │◀── 201 {id, sha256, skills:[…]}│    + запись SkillArchive         │
    │◀── «найдены скиллы: pdf-tools, …» ─────────────────│                                  │
```

На этом шаге архив **не распаковывается**: читается только оглавление zip. Лимиты — D-20. Если проверка не прошла — `422` с понятной причиной («архив больше 20 МБ», «нет SKILL.md», «пути выходят за пределы архива»), и скан создать нельзя.

### 2.3 Шаг 2 — создание и запуск скана

```
web ── POST /scans {type: "agent_skills", agent_config_id: null,
                    config: {archive_id: 7, engines: ["cisco","skillspector"],
                             eval_llm_model_id: 3 | null}} ──▶ control-api
        control-api проверяет: archive_id существует; eval_llm_model_id (если задан) существует
        ◀── 200 Scan {id: 42, status: pending}

web ── POST /scans/42/start ──▶ control-api
        control-api: status=running, phase="Запуск", чистит журнал
                     SCANNERS["agent_skills"] → POST http://scanner-skills:8000/run/42
        scanner-skills отвечает сразу {"status": "started"}, работа идёт в фоне
        если уже идут 2 скана — фаза «В очереди», пока не освободится слот (D-27)
        ◀── 200 Scan {status: running}

web опрашивает раз в 2 с: GET /scans/42  и  GET /scans/42/logs?after_id=…
```

### 2.4 Шаг 3 — что делает `scanner-skills` (фоновый поток)

```
Фаза «Инициализация»
  GET control-api /scans/42                    → config: archive_id, engines, eval_llm_model_id
  GET control-api /llm-models/3   (если задан) → base_url, api_key, model
  проверка: тип скана agent_skills, движки из списка известных

Фаза «Получение архива»
  GET control-api /skill-archives/7/content    → байты zip во временную папку /tmp/skills-42/
  сверка sha256 с записью SkillArchive

Фаза «Распаковка»
  свой извлекатель: каждую запись проверяем ДО записи на диск
    ├─ путь выходит за папку / абсолютный      → отказ архива
    ├─ симлинк                                → отказ архива
    ├─ зашифрованная запись                    → отказ архива
    ├─ превышен лимит по реально прочитанным байтам → отказ архива
    └─ ок → /tmp/skills-42/src/…
  поиск всех SKILL.md → список скиллов (папка с SKILL.md = скилл)
  отказ архива ⇒ сразу к «Сохранение результатов» с вердиктом block (см. R-08)

Фаза «Статический анализ»   (движки параллельно, каждый — отдельный процесс)
  для каждого скилла:
    /opt/engines/cisco/bin/skill-scanner scan <skill_dir> --use-behavioral
        --trusted-rule-pack rules/cisco-pack --format json --output cisco.json
    /opt/engines/skillspector/bin/skillspector scan <skill_dir> --no-llm
        --yara-rules-dir rules/yara -f json -o skillspector-static.json
  у каждого процесса: таймаут, код возврата, stderr в журнал (обрезанный)

Фаза «LLM-анализ»            (этап LLM, D-37; в MVP фазы нет)
  Cisco:        тот же запуск + --use-llm, креды LLM — в env процесса, meta выключен
  SkillSpector: второй запуск без --no-llm, креды в env (SKILLSPECTOR_PROVIDER=openai_compatible …)
  находки LLM-прогона добавляются к статическим, ничего не удаляется

Фаза «Сохранение результатов»
  разбор JSON обоих движков → единая схема находки
  вердикт (D-10) + флаг complete
  PATCH control-api /scans/42 {status: completed, phase: "Завершено", results: {…}}
  DELETE control-api /skill-archives/7/content  → файл архива удаляется (D-22), и при failed тоже
  /tmp/skills-42 удаляется в любом случае
```

Любая ошибка сервиса (control-api недоступен, архив пропал, оба движка упали) → `failed` + текст в `Scan.error`, как у остальных сканеров. Ошибка одного движка — не `failed`, а `complete: false` (D-23).

## 3. Риски и открытые вопросы

Формат: что может сломаться → что предлагаю → вопрос. После ответа риск получает статус, а решение — номер `D-NN`.

### Модель данных

**R-01. `agent_config_id` → nullable задевает чужой код** — закрыт → D-15
Все четыре runner'а читают `scan["agent_config_id"]`, web показывает агента в списке сканов, `list_scans` фильтрует по агенту. Если ослабить колонку, а какой-то код не проверит `null`, упадёт не наш сканер, а страница списка или чужой runner.
Предлагаю: nullable + проверка в `create_scan` по типу + `null`-безопасный web. Runner'ы других сканеров проверяют тип скана раньше чтения агента — проверю каждый при реализации.
Вопрос: делаем nullable сейчас или ждём решения лида по «цели сканирования» (R-02)?

**R-02. Единая сущность «цель сканирования» переделает модель** — закрыт → D-15 (риск лишней миграции принят)
Если лид введёт `Target` (репозиторий/архив/MCP), `SkillArchive` и `Scan.agent_config_id` придётся мигрировать второй раз.
Предлагаю: `SkillArchive` минимальный, чтобы его можно было превратить в `Target(kind=archive)` одной миграцией.
Вопрос: делаем сейчас или ждём встречи?

### Движки

**R-03. Оба движка или один** — закрыт → D-16
Два движка = вдвое больше разбора форматов, размер образа и время скана. Один = меньше покрытие (по прогону: Cisco пропустил persistence в bash, SkillSpector без LLM занижает риск скриптов).
Предлагаю: два в MVP, окончательно — после прогона с LLM.

**R-04. Форматы JSON движков меняются** — закрыт → D-17
SkillSpector помечен как Alpha; у Cisco уже вышла 2.2.2, а проверял я 2.1.0. Любой апдейт может сломать разбор.
Предлагаю: жёсткие версии; незнакомые поля игнорировать, отсутствующие → `null` (как у promptfoo); при обновлении — прогон корпуса и сравнение.
Вопрос: кто и когда обновляет движки — по необходимости или раз в N недель?

**R-05. YARA-правила должны работать в двух разных движках YARA** — закрыт → D-18
Cisco использует **YARA-X** (`yara_x`), SkillSpector — классическую **libyara** (`yara-python`). YARA-X строже и в части синтаксиса несовместим. Правило, рабочее в одном, может не скомпилироваться в другом, и движок упадёт на загрузке правил.
Предлагаю: писать правила в общем подмножестве синтаксиса; при сборке образа компилировать каждое правило обоими движками, чтобы сломанное правило ловилось на сборке, а не на скане.
Вопрос: ок или держим два разных набора правил?

**R-06. Уязвимости в самих движках** — принят (D-19)
Движки разбирают недоверенный контент (YAML, Python AST, zip, `.pyc` у Cisco). Баг парсера = выполнение кода в контейнере сканера. А у контейнера есть доступ к control-api без аутентификации (может менять любые сканы) и LLM-ключ текущего скана.
Предлагаю: процессы движков от отдельного непривилегированного пользователя, read-only файловая система кроме временной папки, лимиты CPU/памяти на процесс.
Вопрос: делаем это в MVP или принимаем риск до прод-версии?

### Приём архива

**R-07. Лимиты загрузки и DoS через загрузку** — закрыт → D-20
FastAPI не ограничивает размер multipart сам: без явной проверки можно залить гигабайты во временные файлы control-api. Zip с огромным центральным каталогом съест память ещё до проверки записей.
Предлагаю: читать поток с ограничением; лимиты — архив 20 МБ, распакованный 100 МБ, 2000 записей, сжатие одной записи ≤ 100:1, центральный каталог ≤ 4 МБ.
Вопрос: согласен с цифрами?

**R-08. Вредоносный архив — это `failed` или `completed + block`** — закрыт → D-21
Zip slip, симлинки, шифрование не пропускаем дальше. Но если показать это как ошибку скана, пользователь решит, что сломалась платформа.
Предлагаю: если признаки атаки видны на загрузке (control-api) — `422` с понятной причиной. Если только при распаковке в сканере — `completed`, вердикт `block`, находка «архив содержит пути за пределами папки».
Вопрос: согласен?

**R-09. Хранение возможной малвари** — закрыт → D-22
Архивы лежат в томе `control-api-data` рядом с SQLite, API без аутентификации.
Предлагаю: скачивать архив из UI нельзя; архив удаляется вместе со всеми сканами, которые на него ссылаются; плюс авто-удаление через N дней.
Вопрос: сколько хранить? Нужно ли вообще хранить после скана, или удалять сразу после завершения?

**R-10. Несколько скиллов в одном архиве** — закрыт → D-13
Архив может содержать 1 или 20 скиллов. Каждый — отдельный запуск движков, время растёт линейно.
Предлагаю: разрешить, с лимитом (например, 10 скиллов на архив), вердикт — по каждому скиллу и общий (худший).
Вопрос: разрешаем пачки или один архив = один скилл?

### Отчёт и вердикт

**R-11. Пороги вердикта** — закрыт → D-12
В прогоне оба движка дали `MEDIUM` легитимному скиллу, который просто ходит в API погоды. Если `medium → review`, большинство нормальных скиллов будут «требует проверки», и на вердикт перестанут смотреть.
Варианты:
- (а) `critical → block`, `high/medium → review`, иначе `pass`;
- (б) `critical → block`, `high → review`, `medium/low` — видны в отчёте, но вердикт `pass`.
Предлагаю (б).
Вопрос: какой вариант?

**R-12. Объединение находок двух движков** — закрыт → D-14
Движки по-разному указывают строку (у Cisco для `SKILL.md` часто `line: null`) и по-разному называют категории. Склейка по `(file, line, category)` будет то дублировать, то склеивать разное.
Предлагаю: в MVP не склеивать, а группировать по файлу с колонкой «движок». Склейку — после того, как увидим реальные отчёты на корпусе.
Вопрос: ок?

**R-13. Один движок упал** — закрыт → D-23
Что показывать, если Cisco отработал, а SkillSpector упал (или наоборот)?
Предлагаю: `completed`, флаг `complete: false`, в отчёте явно «SkillSpector не отработал: <причина>»; если упали оба — `failed`.
Вопрос: согласен?

### LLM

**R-14. Заголовки opencode** — закрыт → D-24
Ни один движок не умеет добавлять `x-opencode-session` / свой `User-Agent`. Если судья — opencode.ai, LLM-режим работать не будет.
Варианты:
- (а) другой OpenAI-совместимый провайдер или локальная модель;
- (б) LLM-трафик движков через compose-сервис `proxy` (`HTTPS_PROXY` + доверие CA прокси) — но тогда запросы сканера попадут в `/events` под `demo-session-1`.

Вопрос: какой провайдер планируем для судьи?

**R-15. Стоимость и время LLM-режима** — закрыт → D-25
SkillSpector в LLM-режиме вызывает несколько LLM-узлов (`semantic_security_discovery`, `semantic_developer_intent`, `semantic_quality_policy`, `meta_analyzer`). Плюс Cisco. Плюс отказы провайдера на вредоносном контенте.
Предлагаю: LLM выключен по умолчанию; `SKILLSPECTOR_TEMPERATURE=0` и `SKILLSPECTOR_SEED` для воспроизводимости; `SKILLSPECTOR_OUTPUT_LANGUAGE` — русский, если работает; отказ модели = «LLM-анализ не выполнен», а не «чисто».
Вопрос: ок?

**R-16. Утечка содержимого наружу** — закрыт → D-26 (риск принят)
С LLM содержимое скилла уходит провайдеру. SkillSpector ещё и ходит в OSV.dev с именами зависимостей. Отключающего OSV флага у него нет, есть только `SKILLSPECTOR_OSV_TIMEOUT`; без сети он откатывается на встроенный список.
Вопрос: разрешаем выход в OSV.dev или режем сеть сервису, кроме LLM-провайдера?

### Эксплуатация

**R-17. Параллельные сканы и ресурсы** — закрыт → D-27
Каждый скан = 2–4 тяжёлых процесса (у Cisco старт ~7 с, в нём magika/onnx). Пять сканов одновременно на ноутбуке = заметная нагрузка, и сейчас ничто её не ограничивает.
Предлагаю: семафор в сервисе — не больше 2 сканов одновременно, остальные ждут с фазой «В очереди».
Вопрос: ок?

**R-18. Образ и сборка** — закрыт → D-28
Два набора зависимостей (LiteLLM, magika/onnx, LangChain/LangGraph, YARA-X, libyara), SkillSpector тянется из git при сборке. Колёса Cisco есть под linux x86_64 и aarch64, то есть сборка и на WSL2, и на Mac (arm64) должна пройти — но я её не проверял. Размер образа не мерил.
Вопрос: есть ограничения по размеру образа или по сети при сборке (сборка в CI без интернета)?

**R-19. Перезапуск сервиса посреди скана** — принят (как у остальных сканеров)
`fail_interrupted_scans` на старте переводит такие сканы в `failed` — копия поведения `scanner-promptfoo`.

**R-20. Проверка без автотестов** — закрыт → D-29
`AGENTS.md` запрещает тест-фреймворк без запроса. А без прогона корпуса любое обновление движка или правила может молча ухудшить детект.
Предлагаю: не тест-фреймворк, а скрипт `scanner/skills/eval/run_corpus.sh` с таблицей «скилл → вердикт», запускается руками.
Вопрос: можно добавить корпус и скрипт в репозиторий или держим их отдельно?

### Новые вопросы после решений 2026-10-10

**R-21. Удаление архива после скана (D-22) против повторного использования** — закрыт → D-30
Сейчас загрузка с тем же sha256 возвращала бы существующий `SkillArchive`. Но если архив удаляется после первого скана, второй скан по той же записи упадёт: файла уже нет. Плюс архивы, по которым скан так и не запустили, должен кто-то удалять — а в control-api нет планировщика.
Предлагаю: один архив = один скан (без дедупа по sha256: каждая загрузка — новая запись, sha256 храним только для отчёта). Чистка «брошенных» архивов старше 24 ч — лениво: при старте control-api и при каждой новой загрузке. Скан, у которого архив уже удалён, при запуске падает с понятным текстом «архив удалён, загрузите заново».
Вопрос: ок?

**R-22. `hooks` и другие проверки frontmatter видит только SkillSpector** — закрыт → D-31
Cisco прогоняет YARA по `SKILL.md` без frontmatter, поэтому правило на `hooks` у него не срабатывает (проверено). Если SkillSpector упал (D-23), `hooks` в отчёте не будет вообще, хотя это одна из самых опасных вещей (код выполняется без участия модели).
Варианты:
- (а) принять: при `complete: false` пользователь и так видит, что проверка неполная;
- (б) маленькая своя проверка в обвязке: разобрать frontmatter как YAML и отметить `hooks`, `allowed-tools: Bash` без ограничений, `` !`…` `` в теле. Это не движок, а ~30 строк разбора структуры, которую YARA не выражает.

Предлагаю (б).
Вопрос: (а) или (б)?

**R-23. `pack.yaml` для Cisco дублирует метаданные правил** — закрыт → D-35
Cisco требует, чтобы `description` в `pack.yaml` совпадал с `meta` правила, а `category` была из его фиксированного списка; иначе сервис не стартует. Два места, которые надо держать в синхроне вручную.
Предлагаю: `pack.yaml` не вести руками, а генерировать скриптом из `meta` `.yara`-файлов при сборке образа (там же — компиляция YARA-X и libyara, D-18).
Вопрос: ок?

**R-24. Плавающие транзитивные зависимости движков** — закрыт → D-32
Мы закрепили версии движков (D-17), но их зависимости заданы диапазонами: у Cisco, например, `litellm>=1.84.0,<2` — и в его же `pyproject.toml` есть комментарий про скомпрометированные релизы LiteLLM на PyPI. Каждая пересборка может притащить новые версии, в том числе вредоносную. Сборка невоспроизводима.
Предлагаю: lock-файл с хэшами на каждый venv (`uv pip compile --generate-hashes` → `requirements-cisco.lock`, `requirements-skillspector.lock`), установка с `--require-hashes`. Обновление lock — вместе с обновлением движка (D-17).
Вопрос: делаем?

**R-25. Таймауты** — закрыт → D-33
Cisco стартует ~7 с на скилл, при 10 скиллах статика ≈ 1–1,5 мин; с LLM — минуты на скилл. Повисший процесс без таймаута держит слот очереди (D-27) навсегда.
Предлагаю: таймаут на один запуск движка по одному скиллу — 300 с (`SCAN_ENGINE_TIMEOUT`), на весь скан — 30 мин (`SCAN_TOTAL_TIMEOUT`); превышение у движка = он «не отработал» (D-23), у скана — `failed`.
Вопрос: ок с цифрами?

**R-26. Уверенность находок (confidence)** — закрыт → D-34
SkillSpector отдаёт `confidence` (0–1) у каждой находки, Cisco — нет. Вердикт (D-12) смотрит только на severity: HIGH с confidence 0,3 тоже даст `review`.
Предлагаю: в MVP confidence не учитывать, но показывать в отчёте; пересмотреть по корпусу.
Вопрос: ок?

### Пересмотр после master `90ee1a4` (2026-10-12)

**R-27. Скиллы из git-репозитория** — закрыт → D-42
`SkillAsset` уже умеет источник `repository`. Если сканер поддержит только zip, для таких активов он будет «недоступен», хотя актив создать можно.
Предлагаю: поддержать оба источника в MVP. Клонирование — копия `repo.py`/`git_auth.py` из `scanner-semgrep` (как принято: общий код не выносится), `--depth 1`, без сабмодулей, `core.symlinks=false`.
Вопрос: делаем git сразу?

**R-28. Один контейнер или координатор + воркеры, как у MCP** — закрыт → D-43
`scanner-mcp` — координатор, который рассылает задачи в отдельные контейнеры движков (один образ, `WORKER_ENGINE`). Наш D-11 — один контейнер, движки как подпроцессы.
Предлагаю: один контейнер `scanner-skills` с подпроцессами и hardening из D-41. Два движка на Python, оба короткие; координатор — это ещё 2 сервиса в compose и HTTP между ними без выигрыша для MVP.
Вопрос: ок или делаем по образцу MCP ради единообразия?

**R-29. Лимиты загрузки — у лида свои** — закрыт → D-44
В `skill_assets.py` уже: архив ≤ 50 МиБ, ≤ 5000 файлов, распакованный ≤ 250 МиБ, `..`/абсолютные пути и симлинки — `422`. Нет: проверки степени сжатия, зашифрованных записей, наличия `SKILL.md`. Наш D-20 строже (20/2000/100 МБ, 100:1).
Предлагаю: загрузку не трогать (лимиты лида), а в сканере добавить то, чего нет: сжатие ≤ 100:1, зашифрованные записи → находка/`block`, «нет ни одного `SKILL.md`» → `failed` с понятным текстом. D-20 считать заменённым лимитами лида.
Вопрос: ок или правим валидацию в `skill_assets.py` (это код лида)?

**R-30. Лимит «10 скиллов» (D-13) и репозитории** — закрыт → D-45
Для zip 10 скиллов — нормально, но git-репозиторий-сборник легко содержит 30–100 скиллов.
